# IDEAL — consensus-sim

## 理想

consensus-sim は、コンセンサスアルゴリズムの本質を私自身が徹底的に理解し、最終的に新たなコンセンサスアルゴリズムを提案できるようになるための実験装置である。時間・技術・予算の制約をすべて外したとき、次の 2 本柱が同じ重みで実現している(着手は 1 → 2 の順):

1. **理解の超促進** — 高く抽象化されたコンセンサスモデル上の精緻なシミュレーション(精緻とはネットワーク忠実度ではなく、抽象モデル上のあらゆるパターンを操作・観測し尽くせる UI/UX を指す)を、洗練された UI/UX で観測・介入でき、攻撃を統一された形式で記述・実行・可視化でき、それが私のアルゴリズム本質理解を加速している。攻撃一覧が実験の入口であり、攻撃を選んで数クリックで成立の全過程が自動で展開され、そこから巻き戻し・介入・パラメータ変更で「なぜ成立するか/どう防げるか」を探索できる — 理解が「見る」から始まり「いじる」へ進む導線がある。
2. **形式検証付き提案** — その抽象モデルと攻撃の形式体系を参照した Lean による形式化・形式検証を備えた、新アルゴリズムの提案ができる。

攻撃の形式体系は、既存研究の分類・体系表を超えて「記述 → 実行 → 可視化」まで一貫して機械可読であり、既知の攻撃はその体系の例にすぎず、体系そのものが柱 2 の Lean 形式化の対象になる。体系の一般性は例の数で裏づけられる: `essences/deep-research-report.md`(Ethereum PoS コンセンサス攻撃の体系的レビュー)に整理された攻撃のうち最抽象モデルの語彙で表現できるものはすべて — 攻撃だけでなく、それを緩和するプロトコル側の仕組み(proposer boost・エクイボケーション割引・justified チェックポイント切替(切替窓 / unrealized justification)・スラッシング・inactivity leak)も含めて — この体系で記述・実行・可視化でき、攻撃が成立する条件と緩和が効く条件の両面を同じ装置で観測できる。緩和策は Ethereum の実仕様に準拠し、導入時期に応じたプロトコルプリセット(phase0 / merge / current)で「どの時点の Ethereum に対する攻撃か」を切り替えて観測できる。

今回のスコープは柱 1 のみ(攻撃の形式体系、そのために必要なプロトコルパラメータ化(committee・proposer boost・緩和策・プリセット)、チェーン状態(ブロックへの投票・証拠の取り込み)、ステークと罰則のモデル化、レポート由来の攻撃ライブラリを含む)。柱 2 は「対象外」に延期として記録する。

## 不変条件

- 現 IDEAL を満たすソフトウェアとして最高のものであると自信を持って言える状態を常に目指す。
- 優先順位は **モデルの正しさ・決定性 > UI/UX の洗練 > 開発速度**。理解促進が目的なので、雑な UI で機能だけ揃えるのは目的を外す。ただし UI の磨き込みでモデルの正しさの検証が後回しになるのは本末転倒。
- 現代の Web アプリケーションとして独自性の高い印象(AI 生成感のなさ、パッと見で与える特徴的な印象)と利便性を両立し、意図が伝わりやすく情報粒度が適切な表現を用いた洗練された UI を提供する。
- コア(モデル・プロトコル層)は抽象境界を崩さない。より具体的な抽象レベルを将来追加できる設計への投資は、目先の単純さに勝る。ただし UI は最抽象レベル専用に作ってよい(UI の汎用化は不要)。

- 攻撃ライブラリの各攻撃は、その攻撃が突く本質(例: バランシング = 正直票の割れの維持、アバランチ = 秘匿ブロック列の一斉公開、Ex-Ante = 保留したブロックと投票を時機を計って公開し正直ブロックを排除)が再現できていれば最抽象モデル上の簡約版でよい。

  - 説明文をパネルに常駐させず、補足はホバー/ⓘ 等の要求時表示に退避する。操作の自明さは部品と配置で担保する。
  - 色・余白・文字サイズ・書体は単一のデザイントークン(`src/ui/tokens.css`)に集約し、UI のスタイル定義はそこから参照する。余白と文字サイズは固定の尺度(4/8px の倍数、3〜4 段の文字階層)に従う。

  - 色は無彩色の地に、意味を持つ色(justified/finalized・攻撃者・バリデータ識別・差分強調)だけを置く。
  - テーマは OS 設定(prefers-color-scheme)に追従するライト/ダークを既定とし、手動切替で上書きできる。
  - 情報設計の再編(パネル配置・操作盤の位置・折り畳みの有無)は、C6・C7・C8 の制約の範囲内で周回が自律で行ってよい。ただし承認済みの見た目を変える再編は ask で人間の再承認を得る。
- ドメイン駆動設計ベースで実装する: ドメイン層(最抽象モデル・プロトコル骨格・攻撃の形式体系)を UI・インフラから独立したモジュールとして分離する。ドメイン層は「本質的仕様(モデル)」`src/domain/model/` と「シミュレーション上の制約」`src/domain/sim/` の 2 モジュールに分割する。本質的仕様は、柱 2 の Lean 形式化がそのまま対象とする定義(型とその意味論) — 識別子のソート / Checkpoint / Vote / Block(body を含む)/ BlockTree / Equivocation / 観測時点と View / ChainState / ProtocolParams / プロトコルプリセット / 初期条件と予定表 / メッセージ参照 / ネットワークモデル(公開の記録・配送規則・遅延上限 d)/ スロット進行・fork choice・finality・取り込みの意味論 / 攻撃の 3 つ組・攻撃者の行動の基底と語彙・攻撃目標述語・戦略 — を置く。シミュレーション上の制約は、本シミュレータの都合で定めるもの — シナリオ / 介入キュー / 手動介入の指定 / 既定実行構成 / localStorage コーデック / シードから予定表を導く乱数生成器 / バリデータ人名 / バリデータ数 4〜10 / フォーク上限 4 など — を置く。振り分けの判定基準は「柱 2 の定理を述べ、証明するのに要る定義か」である。
- 抽象レベルは複数選定可能な構想であり、今回構築するのは最抽象モデルのみ。最抽象モデルは、メッセージの層(各バリデータの View)とチェーン状態の層(ブロックに取り込まれた投票・証拠から枝ごとに定まる状態)の 2 層を持ち、committee 割当と proposer boost に加え、緩和策(fork choice 規則・エクイボケーション割引・justified チェックポイント切替)と罰則(スラッシング・inactivity leak)をプロトコルパラメータとして含み、バリデータごとのステークをチェーン状態として持つ。緩和策の意味論は Ethereum の実仕様に準拠する(細部の簡約は裁量)。より具体的なレベル(デルタや離散イベント刻み、shuffling・報酬を含む Gasper 完全意味論、確率的ネットワーク)は将来の追加であり、コア設計はその追加を妨げないこと。
- エポック長は 4 スロット固定とする(裁量で設定可にしてよい)。
- ジェネシスは扱わない。これまで続いてきたブロックチェーンの、エポック先頭のスロット(これをスロット 0 とする)から開始する。木の根は開始時点で全バリデータが finalized と合意している錨ブロック 1 個とする。
- スロット s のプロポーザーと committee の予定表は初期条件(ProtocolParams・シード)から決定的に導出し、全バリデータ(攻撃者を含む)が知る公開情報とする。プロポーザーはラウンドロビン(骨格の規則であり、パラメータではない)。
- 型は次を参照実装とする(等価な改良は裁量。ただし意味論の変更は人間に戻す):
  - 識別子は互いに区別されるソートとする: `ValidatorIndex`(Lean では Fin n)、`SlotIndex`・`EpochIndex`(ℕ)、`BlockIndex`(同値判定可能な抽象 id)、`Stake`(非負の有理数)。実装ではブランド型等で混用を防ぐ。`BlockIndex` は同一性だけを担い、fork choice とチェックポイント比較のタイブレークに使う全順序は骨格の規則として明示する。
  - `Checkpoint = {epoch: EpochIndex, block: BlockIndex}`。ある枝のエポック e のチェックポイントは、その枝上でエポック e の先頭スロット以前の直近のブロックを block に持つ。境界スロットが空なら、同じブロックが連続するエポックのチェックポイントになる。
  - `Vote = {validator: ValidatorIndex, slot: SlotIndex, head: BlockIndex, source: Checkpoint, target: Checkpoint}`(head は LMD 部分、source → target は FFG 部分。整形条件: target.epoch はスロットの属するエポック)。
  - `Block = 錨 {index: BlockIndex, slot: SlotIndex} または 提案 {index: BlockIndex, parent: BlockIndex, slot: SlotIndex, proposer: ValidatorIndex, body: {votes: Vote[], evidence: Equivocation[]}}`(番兵値は置かない)。
  - `Equivocation` = 同一バリデータの相反する 2 メッセージの対で、次の 3 形: 二重提案(同一スロットの 2 ブロック、index の対)、二重投票(同一スロットの内容の異なる 2 投票、または同一 target エポックで target の異なる 2 投票)、包囲投票(source₁.epoch < source₂.epoch < target₂.epoch < target₁.epoch となる 2 投票)。後の 2 形は Casper FFG の可罰条件そのものである。独立したメッセージ型は設けず、相反 2 メッセージが揃った View で成立し、ブロック body に取り込まれる。
  - `Instant = {slot: SlotIndex, phase: 提案 / 投票 / 末}`(観測時点)。スロット内の 3 時点はこの順で、ブロックは提案時に、投票は投票時に公開され、配送を経て以後の時点の View に現れる(到達時点の細部は裁量)。
  - `View = {blockTree: BlockTree, votes: Vote[]}`。バリデータ v が観測時点 t に持つ知識であり、(v, t) は View の座標であって内容ではない。攻撃者集合の観測状態は各攻撃者の View の合併で、座標を持たない。
  - `ChainState(block)` = 錨ブロックからそのブロックまでの枝に取り込まれた投票・証拠と初期ステークから決定的に導出する `{stakes: ValidatorIndex → Stake, justified: Checkpoint, finalized: Checkpoint}`。View の justified / finalized / ステークは、その View の head の ChainState を指す。
  - `ProtocolParams = {committee: 割当方式(全員 / サイズ c をシードから決定的に割当 / エポック分割), boost: 0〜1, forkChoice: GHOST / LMD-GHOST, equivocationDiscount: on/off, checkpointSwitch: {window: on/off, unrealized: on/off}, slashing: on/off, inactivityLeak: {delayEpochs: N, rate: r} / off}`(細部は裁量)。各スロットの committee とプロポーザーは初期条件から導出し、View / Vote / Block は変えない。
  - 初期条件 `InitialConditions = {validatorCount: n, initialStakes: ValidatorIndex → Stake, params: ProtocolParams, seed}`。予定表 `Schedule = {proposerOf: SlotIndex → ValidatorIndex, committeeOf: SlotIndex → ValidatorIndex の集合}` は初期条件から導出される公開情報で、本質的仕様は割当方式ごとの性質だけを定め、シードからの具体的導出(乱数生成器)はシミュレーション上の制約に置く。
  - メッセージ参照 `MessageRef` = (送信者, スロット, 種別: 提案 / 投票) に、公開済みなら個体(ブロックは index、投票は内容全体)を添えたもの。未公開のメッセージも名指せる(攻撃者の保留・選択配送は、この形で自分の未来のメッセージを名指す)。
  - 取り込み規則: 正直なプロポーザーは、自分の View にあって提案する parent の祖先にまだ取り込まれていない投票・証拠をすべて body に取り込む(取り込み期限などの細部は Ethereum に準拠しつつ裁量)。戦略は取り込みを省略できる。
- プロトコルプリセット(名前付きの ProtocolParams の束。攻撃はプリセット名+個別上書きで前提パラメータを宣言する。既定は `merge`):

  | プリセット | 由来 | forkChoice | boost | 割引 | 切替窓 | unrealized | スラッシング | leak |
  |---|---|---|---|---|---|---|---|---|
  | `phase0` | Beacon chain genesis(2020-12) | LMD-GHOST | 0 | off | on | off | on | on |
  | `merge` | The Merge 時点(2022-09) | LMD-GHOST | 0.4 | on | on | off | on | on |
  | `current` | 2023 年 fork choice 修正以降 | LMD-GHOST | 0.4 | on | off | on | on | on |

  committee は全プリセットで既定「全員」、leak は N = 4・r は裁量。
- 攻撃手法の出典と体系表は `essences/deep-research-report.md`(人間が配置した Ethereum PoS コンセンサス攻撃の体系的レビュー)を参照する。その攻撃 ID(A01〜A21)のうち、最抽象モデルの語彙で表現できる 12 件を攻撃ライブラリに収録する(C23)。ネットワーク層(A15〜A17)・クライアント実装差(A18)・PBS/MEV-Boost(A19〜A21)・提案者 DoS(A13、ステークを持たない純ネットワーク攻撃者)は語彙外として収録しない。weak subjectivity(A08)は「対象外」に延期として記録する。A11 の検閲は取引を扱わないため表現せず、多数派による fork choice 支配(リオーグ)として扱う(投票の取り込み省略は行動語彙にあるが、A11 の攻撃目標には含めない)。
- 攻撃の定義(攻撃者集合の条件・攻撃目標・戦略の 3 つ組、C17)は現時点の暫定最適解であり、今後 `idd refine` で十分に変わりうる。コア設計はその改定を妨げないこと。

## 用語

- **最抽象モデル**: バリデータ(プロポーザー/アテスター)・ブロック・投票を主要素とし、committee 割当・proposer boost・緩和策・罰則をプロトコルパラメータとして持ち、メッセージ層(View)とチェーン状態層(取り込み)の 2 層を持ち、バリデータごとのステークをチェーン状態として持つコンセンサスの形式化。時間はスロット刻みで、スロット内に提案・投票・末の 3 つの観測時点を持つ。
- **バリデータ**: シミュレーションの参加者。ネットワーク分断・稼働状態変更等の介入はバリデータ単位で指定する。
- **プロポーザー/アテスター**: ブロックを提案する役割のバリデータ/投票する役割のバリデータ。アテスターはそのスロットの committee に属するバリデータ。
- **committee**: あるスロットで投票するアテスターの集合。割当方式はプロトコルパラメータ(既定は全員、他にサイズ c をシードから決定的に割当、エポック分割 = 各バリデータがエポック内でシードから定まる 1 スロットにだけ投票)。
- **予定表**: 初期条件(ProtocolParams・シード)から導出されるプロポーザーと committee の割当 `{proposerOf, committeeOf}`。全バリデータが知る公開情報。プロポーザーはラウンドロビン。
- **初期条件**: バリデータ数・初期ステーク・プロトコルパラメータ・シードの組。シナリオの一部であり、プロトコルが読む入力。
- **観測時点**: `{slot, phase: 提案 / 投票 / 末}`。View の座標。ブロックは提案時に、投票は投票時に公開される。
- **proposer boost**: スロット s のプロポーザーのブロックを (s, 投票) までに受信したバリデータの、スロット s の fork choice においてのみそのブロックに付く追加重み(committee 総重み × boost)。既定 0.4。
- **取り込み**: プロポーザーが提案ブロックの body に投票・証拠を含めること。正直なプロポーザーは View 内の未取り込み分をすべて取り込む。**取り込みの省略**はその一部を意図的に含めない介入/攻撃者の行動。
- **証拠(エクイボケーションの証拠)**: 同一バリデータの相反する 2 メッセージの対。二重提案・二重投票・包囲投票の 3 形。独立したメッセージ型ではなく、相反 2 メッセージが揃った View で成立し、ブロックに取り込まれる。
- **チェックポイント**: `{epoch, block}`。ある枝のエポック e のチェックポイントは、その枝上でエポック e の先頭スロット以前の直近のブロック(先頭スロットにブロックがあればそれ、無ければそれ以前の最も新しい祖先。Ethereum に準拠)。境界スロットが空なら同じブロックが連続するエポックのチェックポイントになる。
- **チェーン状態**: あるブロックについて、錨ブロックからそのブロックまでの枝に取り込まれた投票・証拠と初期ステークから決定的に導出される、ステーク・justified・finalized(いずれもチェックポイント)の組。View の justified / finalized / ステークは head のチェーン状態。
- **プロトコルパラメータ**: committee 割当方式・サイズ c、proposer boost、fork choice 規則、エクイボケーション割引、justified チェックポイント切替(切替窓・unrealized の 2 スイッチ)、スラッシング、inactivity leak。初期条件の一部。既定は `merge` プリセット。
- **プロトコルプリセット**: Ethereum の実在時点に対応する名前付きのプロトコルパラメータの束(phase0 / merge / current)。攻撃はプリセット名+個別上書きで前提を宣言する。
- **ステーク**: バリデータの重み。枝ごとのチェーン状態であり、初期ステークと取り込み内容から導出する。fork choice の重みと FFG の 2/3 閾値の計算に使い、罰則により減る。
- **罰則**: スラッシングと inactivity leak の総称。チェーン状態のステークを減らすプロトコルパラメータ。
- **緩和策**: fork choice 規則(GHOST / LMD-GHOST)・エクイボケーション割引・justified チェックポイント切替の総称(C27)。proposer boost と罰則は別のプロトコルパラメータとして数えるが、攻撃を未達にする働きは同じく観測の対象とする。
- **スラッシング**: 証拠を取り込んだブロック以降の枝のチェーン状態で、エクイボケータのステークを 0 として扱う罰則。プロトコルパラメータ(on/off)。
- **inactivity leak**: 枝の finalized が N エポック進まないときに発動し、エポックごとにその枝に target 投票が取り込まれていないバリデータのステークを率 r で減らす罰則。プロトコルパラメータ({N, r} / off)。
- **エクイボケーション割引**: View 内で投票の証拠が成立した瞬間から、そのバリデータの投票を fork choice の重みから除外する緩和策(即時・局所・fork choice のみ)。プロトコルパラメータ(on/off)。
- **justified チェックポイント切替**: fork choice の起点とする justified チェックポイントの切替規則。独立した 2 スイッチ: 切替窓(on: エポック内の先頭区間に限る)と unrealized(on: unrealized justification により古い justified しか実現し得ない枝を除外)。プロトコルパラメータ。
- **unrealized justification**: 枝に取り込まれた投票をエポック末を待たずに集計したときに justified となるチェックポイント。
- **エポック**: 4 スロットの区切り。チェックポイントの単位。
- **錨ブロック**: 開始時点で全バリデータが finalized と合意している木の根。ジェネシスの代替。エポック 0 のチェックポイント。
- **ビュー**: あるバリデータがある観測時点に持つ知識 `{blockTree, votes}`。バリデータと観測時点は View の座標であり、内容ではない。
- **投票**: `{validator, slot, head, source, target}`。head は GHOST 系 fork choice の先頭支持(LMD 部分。LMD かどうかはプロトコルパラメータ)、source/target は FFG 部分のチェックポイント対で、正直者はエポックごとに 1 度だけ決め、同じエポックの投票で繰り返す。
- **投票先指定**: 特定バリデータのスロット s の投票の head/target をその View 内のブロックから、source を View 内の枝のチェックポイントから指定する介入。
- **メッセージ参照**: (送信者, スロット, 種別) に、公開済みなら個体を添えたメッセージの名指し。未公開のメッセージも名指せる。
- **受信者集合**: 遅延・欠落の介入で、そのメッセージが遅延・欠落する相手のバリデータ集合(既定は全員)。攻撃者はこれで自分のメッセージの保留と選択配送を行う。
- **状態表**: チェーン表示の下に置く、行 = バリデータ・列 = スロットの表。セルの表示項目は UI から動的に選択でき、他バリデータとの差分がある箇所を強調表示する。
- **操作盤**: プロトコルパラメータ・介入・シナリオの操作系を集約した、主役(チェーン表示・状態表)より小さい面積の領域。
- **デザイントークン**: 色・余白・文字サイズ・書体の単一の定義。UI のスタイル定義はここから参照する。
- **稼働状態**: バリデータの 3 状態。オンライン稼働/オンライン停止(提案・投票をしないが受信は続く)/オフライン(送受信とも遮断されビューが凍結)。復帰はいずれもオンライン稼働に戻る。
- **フォーク**: ブロック木上の競合するブランチ。フォーク作成 = 提案ブロックの parent をプロポーザーの View 内のブロックから指定する介入。
- **フォーク数**: 神視点の木(公開済み全ブロック)で、最新の finalized ブロックを根とする部分木の葉の数。フォーク作成の指定は、未実行の指定を含めてこれが 4 を超えない範囲でのみ受け付ける。
- **神視点**: 公開済み全ブロック・全投票(公開の記録)と各枝のチェーン状態を重ねた大域の木。チェーン表示はこれを示し、攻撃目標述語はこれで評価する。
- **分断**: 指定したバリデータ集合間のメッセージが届かなくなる介入。
- **エクイボケーション**: 同一バリデータによる二重提案・二重投票・包囲投票。
- **包囲投票**: 同一バリデータの 2 投票で、一方の source → target がもう一方の source → target をエポックで外側から包むもの。Casper FFG の可罰条件。
- **可罰性**: 安全性違反が起きたとき、神視点に合計ステーク 1/3 以上の証拠が存在すること。Casper FFG の accountable safety。
- **決定性**: 同一シナリオ(シードを含む)から同一の実行結果が再現されること。
- **シナリオ**: 初期条件+手動介入の列+高々 1 つの攻撃の保存単位(localStorage に保存)。
- **攻撃**: (攻撃者集合の条件, 攻撃目標, 戦略) の 3 つ組。現時点の暫定定義。
- **攻撃者集合の条件**: 攻撃者として振る舞うバリデータの空でない部分集合が満たすべき条件(人数の下限、または初期ステーク比率の下限)。条件を満たす具体的な集合を束ねたものが攻撃の実行。
- **前提(攻撃の)**: 攻撃が成立する環境の宣言。プロトコルパラメータ(プリセット名+上書き)と遅延上限 d。
- **公開/配送**: 攻撃者の行動の 2 つの基底(C18)。公開は自分名義のメッセージを任意の内容・時機・受信者集合で出すこと、配送は正直者のメッセージの到達を遅らせる(最大 d スロット)か欠落させること。
- **攻撃目標**: 攻撃の成否を判定する観測可能な述語の非空な列(通常は長さ 1)。神視点で毎スロット境界に、先頭から順に評価する。種類は安全性違反・活性停止・リオーグ・攻撃者ステーク比率。
- **リオーグ(事象)**: 正直バリデータの head が、直前スロットの head の子孫でないブロックに移ること。
- **攻撃者ステーク比率**: いずれかの正直バリデータの head 枝のチェーン状態における、攻撃者集合の合計ステーク ÷ 全バリデータの合計ステーク。
- **戦略**: 各スロット境界で、攻撃者が観測している状態(攻撃者集合の全 View の合併と予定表)を入力に、その境界での攻撃者の行動(C18 の能力範囲)を決める規則。固定の介入列は戦略の特殊ケース。
- **既定実行構成**: 攻撃ごとに宣言する、攻撃者集合の条件を満たすバリデータ数・初期ステーク・攻撃者集合・前提・攻撃パラメータ・自動再生の終了スロットの組。攻撃一覧の行を選ぶとシナリオの初期条件として提案される。
- **自動再生**: スロットが一定の間隔で自動的に送られる再生。一時停止・再開ができる。攻撃の自動再生は攻撃一覧の実行開始の操作で始まり、攻撃目標の達成スロットまたは既定実行構成の終了スロットで停止する(C31)。
- **攻撃ライブラリ**: ドメイン層の TypeScript として定義された攻撃の集合。攻撃一覧ページの表はここから導出する。
- **本質的仕様/シミュレーション上の制約**: ドメイン層の 2 モジュール。前者は柱 2 の定理を述べ、証明するのに要る定義(型と意味論)、後者は本シミュレータの都合で定めるもの。型一覧は前者のみ表示する。
- **総点検**: C16 の 3 観点(整合/引き算/複合条件バグ)による自己批判的な点検。記録は `docs/INSPECTION.md`。
