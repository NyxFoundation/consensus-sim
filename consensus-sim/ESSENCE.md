# ESSENCE — consensus-sim

## モチベーション

consensus-sim は、コンセンサスアルゴリズムの本質を私自身が徹底的に理解し、
最終的に新たなコンセンサスアルゴリズムを提案できるようになるための実験装置である。

これまでチームメンバーが Gasper ベースのシミュレーター(M1)を構築してきたが、
根本から設計し直すことになり、今後は主に私が開発する。新設計の核は
「高く抽象化されたモデルを用いた精緻シミュレーション」であり、ここで言う精緻とは
ネットワーク忠実度ではなく、抽象モデル上のあらゆるパターンを操作・観測し尽くせる
UI/UX を指す。

柱 1 を進める中で、理解を超促進するには攻撃手法の形式化が必要だと判断した。
既存研究には攻撃の分類・体系表はあるが、記述→実行→可視化まで一貫して機械可読な
形式として与えたものは(私の認識では)ない。そこで本シミュレータ上に、攻撃を
最抽象モデルの語彙で統一的に記述する体系を持ち、あらゆる攻撃手法をその体系で
記述→実行→可視化できる形に落とし込む。既知の攻撃はその体系の例にすぎず、
体系そのものが柱 2 の Lean 形式化の対象にもなる。攻撃一覧はその実験の入口であり、
攻撃を選んで数クリックで成立の全過程が自動で展開され、そこから巻き戻し・介入・
パラメータ変更で「なぜ成立するか/どう防げるか」を探索できること — 理解が
「見る」から始まり「いじる」へ進む導線 — を目指す。

体系の一般性は例の数で裏づける。`essences/deep-research-report.md`(Ethereum PoS
コンセンサス攻撃の体系的レビュー)に整理された攻撃のうち、最抽象モデルの語彙で
表現できるものはすべて — 攻撃だけでなく、それを緩和するプロトコル側の仕組み
(proposer boost・エクイボケーション割引・justified チェックポイント切替(切替窓 /
unrealized justification)・スラッシング・inactivity leak)も含めて — この体系で
記述・実行・可視化でき、攻撃が成立する条件と緩和が効く条件の両面を同じ装置で
観測できる状態を目指す。緩和策は Ethereum の実仕様に準拠し、その導入時期に応じた
プロトコルプリセット(phase0 / merge / current)で「どの時点の Ethereum に対する
攻撃か」を切り替えて観測できるようにする。

本質的理想は次の 2 本柱で、重要度は等しく、着手は 1 → 2 の順とする:

1. **理解の超促進** — 高く抽象化されたコンセンサスモデル上の精緻なシミュレーションを、
   洗練された UI/UX で観測・介入でき、攻撃を統一された形式で記述・実行・可視化でき、
   それが私のアルゴリズム本質理解を加速する。
2. **形式検証付き提案** — その抽象モデルと攻撃の形式体系を参照した Lean による
   形式化・形式検証を備えた、新アルゴリズムの提案ができる。

今回スコープは柱 1 のみ(攻撃の形式体系、そのために必要なプロトコルパラメータ化
(committee・proposer boost・緩和策・プリセット)、チェーン状態(ブロックへの投票・
証拠の取り込み)の導入、ステークと罰則のモデル化、レポート由来の攻撃ライブラリを
含む。柱 2 は非対応事項に延期として記録)。

## 思想

- 現 ESSENCE を満たすソフトウェアとして最高のものであると自信を持って言える状態を
  常に目指す。
- 現代の Web アプリケーションとして独自性の高い印象(AI 生成感のなさ、パッと見で
  与える特徴的な印象)と利便性を両立する。
- 意図が伝わりやすく、情報粒度が適切な表現を用いた、洗練された UI を提供する。
- 優先順位は **モデルの正しさ・決定性 > UI/UX の洗練 > 開発速度**。
  理解促進が目的なので、雑な UI で機能だけ揃えるのは目的を外す。ただし UI の
  磨き込みでモデルの正しさの検証が後回しになるのは本末転倒。
- **コア(モデル・プロトコル層)は抽象境界を崩さない**ことを優先する。
  より具体的な抽象レベルを将来追加できる設計への投資は、目先の単純さに勝る。
  ただし UI は最抽象レベル専用に作ってよい(UI の汎用化は今回不要)。
- 攻撃ライブラリの各攻撃は、その攻撃が突く本質(例: バランシング = 正直票の割れの
  維持、アバランチ = 秘匿ブロック列の一斉公開、Ex-Ante = 保留したブロックと投票を
  時機を計って公開し正直ブロックを排除)が再現できていれば最抽象モデル上の簡約版で
  よい。committee・boost・緩和策・チェーン状態・ステークと罰則を入れてもなお最抽象
  モデルで表現不能と判明した攻撃は、自律で読み替えず人間に戻す(非対応事項「より
  具体的な抽象レベルの追加」の昇格判断)。
- 攻撃と緩和は同じ体系で両面を観測する: 各攻撃は自分が成立するプロトコルパラメータ
  (プリセット+上書き)を宣言し、既定(`merge` プリセット)では proposer boost・
  緩和策が効いて未達となる攻撃は、そのまま未達と表示する。成功条件の想定どおりに
  成立/緩和しない攻撃があれば、自律でモデルや緩和策の意味論を変えず人間に戻す。
- 次の判断は自律で決めず、必ず人間に戻す:
  (a) ビューの型・ブロック body(取り込み)・プロトコル骨格の意味論の変更
  (source/target の解釈変更、取り込み規則の変更など)、
  (b) UI の見た目・情報設計の大きな方針転換(ただし必須対応事項 30 の刷新において
  前提事項のデザイン方針が許す範囲の再編は除く)、
  (c) 攻撃の定義(攻撃者集合の条件・攻撃目標・戦略の 3 つ組)・攻撃者の能力範囲・
  攻撃目標述語の意味論の変更。

## 前提事項

- 既存 M1 実装は捨てて、ゼロから書き直す。互換性の維持は不要。
- 技術スタックの選定は Atlas Builder の裁量に任せる(描画方式も含む。ただし
  ドメイン層を TypeScript で書くことは必須対応事項 20 の前提である)。
- バックエンドなしの静的 SPA を維持し、GitHub Pages で公開する。UI テキストは日本語。
- 公開は `<リポジトリ根>/.github/workflows/deploy.yml` による GitHub Actions 経由の
  GitHub Pages デプロイで、main への push ごとに `consensus-sim/scripts/ci.sh` を実行し、
  成功したときだけ `consensus-sim/dist/` を公開する。deploy.yml は「checkout → Node 設置
  → このスクリプトを 1 本呼ぶ → dist/ を publish」だけを持つ薄い shim に保つ。PROJECT_ROOT
  の外にあるため Atlas Builder は shim を読み書きできず(サンドボックス境界)、人間が管理
  する。CI の実体 — 依存導入・検査の種類と順序 — は PROJECT_ROOT 内の `scripts/ci.sh` に
  置き、Atlas Builder がこれを保守して契約 — clean install で test・build が exit 0 で
  終わり、`dist/` が相対パス参照で自己完結する — を守る。shim 自体の変更が必要になった
  ときは Human-input Recommendation を上げる。
- UI のデザイン方針 — 「計器(instrument)」: 研究計器としての固有の顔を持ち、
  開いた瞬間に構造が読める分析画面とする。
  - 主役はチェーン表示と状態表である。標準的な PC の画面幅の初期表示で、スクロール
    なしにこの 2 つが画面面積の過半を占め、ブロック木は分岐・justified/finalized の
    確定・head の移動が図として読める大きさで描く。操作系(プロトコルパラメータ・
    介入・シナリオ)はそれより小さい面積の操作盤に集約する。この主役の規則は
    チェーン表示ページに対するものであり、型一覧ページは必須対応事項 8 の独自
    レイアウトに従う。
  - フォーム部品はブラウザ既定の見た目のまま使わず、アプリ自身の統一部品で組む。
  - 説明文をパネルに常駐させず、補足はホバー/ⓘ 等の要求時表示に退避する。操作の
    自明さは部品と配置で担保する。
  - 色・余白・文字サイズ・書体は単一のデザイントークンに集約し、UI のスタイル定義は
    そこから参照する。余白と文字サイズは固定の尺度(4/8px の倍数、3〜4 段の
    文字階層)に従う。
  - 書体は意図して選定した 1 組を、日本語・英語・等幅(数値・ID・時刻・コード的
    情報)の 3 用途に割り当てる。外部フォントサービスには依存しない。
  - 色は無彩色の地に、意味を持つ色(justified/finalized・攻撃者・バリデータ識別・
    差分強調)だけを置く。
  - テーマは OS 設定(prefers-color-scheme)に追従するライト/ダークを既定とし、
    手動切替で上書きできる。
  - 情報設計の再編(パネル配置・操作盤の位置・折り畳みの有無)は、必須対応事項
    6・7・8 の制約の範囲内で Atlas Builder が自律で行ってよい。最終形は必須対応事項
    30 の人間レビューで判定する。
- ドメイン駆動設計ベースで実装する: ドメイン層(最抽象モデル・プロトコル骨格・
  攻撃の形式体系)を UI・インフラから独立したモジュールとして分離し、ドメイン層の
  コードは「用語」節のユビキタス言語と一致する命名を用いる。ドメイン層は React 等の
  UI 技術に依存しない。
- ドメイン層は「本質的仕様(モデル)」と「シミュレーション上の制約」の 2 モジュールに
  分割する。本質的仕様は、柱 2 の Lean 形式化がそのまま対象とする定義(型とその意味論)
  — 識別子のソート / Checkpoint / Vote / Block(body を含む)/ BlockTree / Equivocation /
  観測時点と View / ChainState / ProtocolParams / プロトコルプリセット / 初期条件と予定表 /
  メッセージ参照 / ネットワークモデル(公開の記録・配送規則・遅延上限 d)/ スロット進行・
  fork choice・finality・取り込みの意味論 / 攻撃の 3 つ組・攻撃者の行動の基底と語彙・
  攻撃目標述語・戦略 — を置く。シミュレーション上の制約は、本シミュレータの都合で
  定めるもの — シナリオ / 介入キュー / 手動介入の指定 / 既定実行構成 / localStorage
  コーデック / シードから予定表を導く乱数生成器 / バリデータ人名 / バリデータ数 4〜10 /
  フォーク上限 4 など — を置く。振り分けの判定基準は「柱 2 の定理を述べ、証明するのに
  要る定義か」であり、総点検で点検する(必須対応事項 28)。
- 抽象レベルは複数選定可能な構想であり、今回構築するのは最抽象モデルのみ。最抽象
  モデルは、メッセージの層(各バリデータの View)とチェーン状態の層(ブロックに
  取り込まれた投票・証拠から枝ごとに定まる状態)の 2 層を持ち、committee 割当と
  proposer boost に加え、緩和策(fork choice 規則・エクイボケーション割引・justified
  チェックポイント切替)と罰則(スラッシング・inactivity leak)をプロトコルパラメータ
  として含み、バリデータごとのステークをチェーン状態として持つ(必須対応事項 3・25・
  26・27・29)。緩和策の意味論は Ethereum の実仕様に準拠する(細部の簡約は裁量)。より
  具体的なレベル(デルタや離散イベント刻み、shuffling・報酬を含む Gasper 完全意味論、
  確率的ネットワーク)は将来の追加であり、コア設計はその追加を妨げないこと。
- エポック長は 4 スロット固定とする(裁量で設定可にしてよい)。
- ジェネシスは扱わない。これまで続いてきたブロックチェーンの、エポック先頭のスロット
  (これをスロット 0 とする)から開始する。木の根は開始時点で全バリデータが finalized と
  合意している錨ブロック 1 個とする。
- スロット s のプロポーザーと committee の予定表は初期条件(ProtocolParams・シード)から
  決定的に導出し、全バリデータ(攻撃者を含む)が知る公開情報とする。プロポーザーは
  ラウンドロビン(骨格の規則であり、パラメータではない)。
- 型は次を参照実装とする(等価な改良は裁量。ただし意味論の変更は人間に戻す):
  - 識別子は互いに区別されるソートとする: `ValidatorIndex`(Lean では Fin n)、
    `SlotIndex`・`EpochIndex`(ℕ)、`BlockIndex`(同値判定可能な抽象 id)、`Stake`
    (非負の有理数)。実装ではブランド型等で混用を防ぐ。`BlockIndex` は同一性だけを
    担い、fork choice とチェックポイント比較のタイブレークに使う全順序は骨格の規則として
    明示する。
  - `Checkpoint = {epoch: EpochIndex, block: BlockIndex}`。ある枝のエポック e の
    チェックポイントは、その枝上でエポック e の先頭スロット以前の直近のブロックを block に
    持つ。境界スロットが空なら、同じブロックが連続するエポックのチェックポイントになる。
  - `Vote = {validator: ValidatorIndex, slot: SlotIndex, head: BlockIndex, source: Checkpoint, target: Checkpoint}`
    (head は LMD 部分、source → target は FFG 部分。整形条件: target.epoch はスロットの
    属するエポック)
  - `Block = 錨 {index: BlockIndex, slot: SlotIndex} | 提案 {index: BlockIndex, parent: BlockIndex, slot: SlotIndex, proposer: ValidatorIndex, body: {votes: Vote[], evidence: Equivocation[]}}`
    (番兵値は置かない)
  - `Equivocation` = 同一バリデータの相反する 2 メッセージの対で、次の 3 形:
    二重提案(同一スロットの 2 ブロック、index の対)、二重投票(同一スロットの内容の
    異なる 2 投票、または同一 target エポックで target の異なる 2 投票)、包囲投票
    (source₁.epoch < source₂.epoch < target₂.epoch < target₁.epoch となる 2 投票)。
    後の 2 形は Casper FFG の可罰条件そのものである。独立したメッセージ型は設けず、
    相反 2 メッセージが揃った View で成立し、ブロック body に取り込まれる。
  - `Instant = {slot: SlotIndex, phase: 提案 | 投票 | 末}`(観測時点)。スロット内の
    3 時点はこの順で、ブロックは提案時に、投票は投票時に公開され、配送を経て以後の
    時点の View に現れる(到達時点の細部は裁量)。
  - `View = {blockTree: BlockTree, votes: Vote[]}`。バリデータ v が観測時点 t に持つ
    知識であり、(v, t) は View の座標であって内容ではない。攻撃者集合の観測状態は
    各攻撃者の View の合併で、座標を持たない。
  - `ChainState(block)` = 錨ブロックからそのブロックまでの枝に取り込まれた投票・証拠と
    初期ステークから決定的に導出する `{stakes: ValidatorIndex → Stake, justified:
    Checkpoint, finalized: Checkpoint}`。View の justified / finalized / ステークは、
    その View の head の ChainState を指す。
  - `ProtocolParams = {committee: 割当方式(全員 | サイズ c をシードから決定的に割当 | エポック分割: 各バリデータがエポック内でシードから定まる 1 スロットにだけ投票), boost: 0〜1, forkChoice: GHOST | LMD-GHOST, equivocationDiscount: on/off, checkpointSwitch: {window: on/off, unrealized: on/off}, slashing: on/off, inactivityLeak: {delayEpochs: N, rate: r} | off}`
    (細部は裁量)。各スロットの committee とプロポーザーは初期条件から導出し、
    View / Vote / Block は変えない。
  - 初期条件 `InitialConditions = {validatorCount: n, initialStakes: ValidatorIndex → Stake, params: ProtocolParams, seed}`。
    予定表 `Schedule = {proposerOf: SlotIndex → ValidatorIndex, committeeOf: SlotIndex → ValidatorIndex の集合}`
    は初期条件から導出される公開情報で、本質的仕様は割当方式ごとの性質だけを定め、
    シードからの具体的導出(乱数生成器)はシミュレーション上の制約に置く。
  - メッセージ参照 `MessageRef` = (送信者, スロット, 種別: 提案 | 投票) に、公開済みなら
    個体(ブロックは index、投票は内容全体)を添えたもの。未公開のメッセージも名指せる
    (攻撃者の保留・選択配送は、この形で自分の未来のメッセージを名指す)。
  - 取り込み規則: 正直なプロポーザーは、自分の View にあって提案する parent の祖先に
    まだ取り込まれていない投票・証拠をすべて body に取り込む(取り込み期限などの細部は
    Ethereum に準拠しつつ裁量)。戦略は取り込みを省略できる。
- プロトコルプリセット(名前付きの ProtocolParams の束。攻撃はプリセット名+個別
  上書きで前提パラメータを宣言する。既定は `merge`):

  | プリセット | 由来 | forkChoice | boost | 割引 | 切替窓 | unrealized | スラッシング | leak |
  |---|---|---|---|---|---|---|---|---|
  | `phase0` | Beacon chain genesis(2020-12) | LMD-GHOST | 0 | off | on | off | on | on |
  | `merge` | The Merge 時点(2022-09) | LMD-GHOST | 0.4 | on | on | off | on | on |
  | `current` | 2023 年 fork choice 修正以降 | LMD-GHOST | 0.4 | on | off | on | on | on |

  committee は全プリセットで既定「全員」、leak は N = 4・r は裁量。
- 攻撃手法の出典と体系表は `essences/deep-research-report.md`(人間が配置した
  Ethereum PoS コンセンサス攻撃の体系的レビュー)を参照する。その攻撃 ID(A01〜A21)の
  うち、最抽象モデルの語彙で表現できる 12 件を攻撃ライブラリに収録する(必須対応
  事項 23)。ネットワーク層(A15〜A17)・クライアント実装差(A18)・PBS/MEV-Boost
  (A19〜A21)・提案者 DoS(A13、ステークを持たない純ネットワーク攻撃者)は語彙外として
  収録しない。weak subjectivity(A08)は非対応事項に延期として記録する。A11 の検閲は
  取引を扱わないため表現せず、多数派による fork choice 支配(リオーグ)として扱う
  (投票の取り込み省略は行動語彙にあるが、A11 の攻撃目標には含めない)。
- 攻撃の定義(攻撃者集合の条件・攻撃目標・戦略の 3 つ組、必須対応事項 17)は現時点の
  暫定最適解であり、今後 update-essence で十分に変わりうる。コア設計はその改定を
  妨げないこと。

   されている。グラフ上の型を選ぶと右側の内容がその型に切り替わる。かつ人間が
   実ブラウザで確認して承認している。
3. チェーン表示の下に状態表が表示される: 行 = バリデータ、列 = スロットで上部チェーン
   表示の slotIndex と横位置が揃い、セルに表示する項目(head / justified / finalized /
   ステーク / View の要素)を UI から動的に選択でき、他バリデータとの差分がある箇所が
   強調表示される。標準的な PC の画面幅で約 10 スロット分の列が収まり、超過分は
   横スクロールで辿れる。
4. 任意のバリデータの状態(head・justified/finalized・View の内容)を状態表から個別に
   観測でき、分断中は該当バリデータ行の値が分断相手と食い違い(差分強調で視認でき)、
   分断解消後は後続スロットの進行に伴い一致へ収束することが表上で確認できる。
5. UI から (a) 任意のバリデータ集合の分断、(b) バリデータの稼働状態の変更
   (オンライン稼働/オンライン停止/オフライン)、(c) 二重提案・二重投票
   (エクイボケーション)、(d) 特定メッセージの遅延・欠落(受信者集合を指定でき、
   既定は全員)、(e) 提案ブロックの parent 指定(フォーク作成)、(f) 特定バリデータの
   スロット s の投票の head/target をそのバリデータの View 内のブロックから、source を
   View 内の枝のチェックポイントから指定、(g) プロポーザーの次の提案での取り込みの
   省略、をスロット境界で指定でき、指定どおりの結果が次スロット以降の表示で観測できる。
6. 任意の過去スロットに巻き戻すと、その時点の全バリデータの状態が正確に再現される。
7. 介入の列をシナリオとして localStorage に保存し、一覧から再読込して再実行すると
   同一の結果が再現される。
8. finalized 済みのチェックポイントにはすべて finalized の表示(F)が付く
   (最新の finalized のみ F でそれ以前が J に留まる表示をしない)。
9. 介入の指定・取り消しを連続して行っても、無効なイベント(終了スロットが開始スロット
   より前になる指定など)が介入キューに生成・残留しない。
10. 型一覧ページを開くと、ドメイン層の本質的仕様モジュールの型が上から下への依存グラフ
    (他のどの型にも依存しない型が最上段)として表示され、その内容が実装の同モジュールの
    型定義と一致しており、シミュレーション上の制約モジュールの型は表示されない。各型の
    宣言にはその日本語コメントが表示され、コメントを持たない型が無い。
11. 上記のシナリオ操作がすべて、説明書なしで UI 上の操作だけで実行でき、
    各ステップの状態変化が読み取れる。
12. 総点検の記録(3 観点ごとの点検内容・発見した問題・対処)が、改訂で追加された
    必須対応事項の分も含めて残っており、発見された問題がすべて解消済みである。
13. ビルド・型検査・ユニットテスト(コアのモデル・チェーン状態(取り込み・
    ステーク導出・justified/finalized)・fork choice(committee・boost・緩和策
    (割引、切替窓 / unrealized justification)を含む)・罰則(スラッシング・inactivity
    leak)・プリセット・フォーク数・決定性・巻き戻し・攻撃の戦略実行と目標判定を含む)が
    すべて exit 0 で終わる。
14. プロトコルパラメータ(committee 割当方式・サイズ c、proposer boost、fork choice
    規則、エクイボケーション割引、justified チェックポイント切替(切替窓 on/off・
    unrealized on/off)、スラッシング、inactivity leak)とシードを UI から個別に設定でき、
    かつプリセット(phase0 / merge / current)を選ぶと各値が一括で切り替わる。既定は
    `merge`(committee = 全員、boost = 0.4、LMD-GHOST、割引 on、切替窓 on・unrealized
    off、スラッシング on、leak on(N = 4 エポック、率 r は裁量))である。committee を
    全員以外にすると各スロットで committee 所属者のみが投票することが、boost を変えると
    fork choice の結果が変わることが、状態表・チェーン表示で観測できる。
15. 状態表のセル展開で、そのバリデータの head のチェーン状態(各バリデータの
    ステーク・justified・finalized)と、head ブロックの body(取り込まれた投票・
    証拠)が確認でき、同じスロットでも head の枝が異なるバリデータ間でチェーン状態が
    食い違うことが差分強調で視認できる。
16. 攻撃一覧ページを開くと、冒頭に攻撃の形式体系の定義(3 つ組・攻撃者の能力範囲・
    攻撃目標述語)が表示され、続いて攻撃ライブラリの全攻撃が表(列: 攻撃名/出典
    (`essences/deep-research-report.md` の攻撃 ID を含む)/前提(プリセット名+
    上書き・遅延上限 d)/攻撃者集合の条件/攻撃者に必要な能力/攻撃目標(述語の列)/
    戦略の要約/既定実行構成)で表示され、その内容が実装の攻撃ライブラリと一致している。
17. 攻撃一覧の行を選ぶと、その攻撃の既定実行構成(バリデータ数・初期ステーク・
    攻撃者集合・前提・攻撃パラメータ・終了スロット)がシナリオの初期条件として提案され、
    変更の有無にかかわらず実行開始の操作だけで自動再生が始まり、各スロットで戦略が
    生成した行動が攻撃者の印付きで介入一覧・状態表・チェーン表示に現れ、攻撃者
    バリデータがチェーン表示・状態表のいずれでも識別できる。攻撃者集合が
    宣言条件を満たさないときは「条件未満」の表示を付けたまま実行できる。
18. 攻撃目標の達成/未達が毎スロット自動判定され、スロット軸上に述語の段階ごとの
    推移と根拠(例: 「finality 停止 6 スロット目」「第 1 段 達成 @slot 12」)が表示される。
19. 攻撃ライブラリの全 12 攻撃を、それぞれの既定実行構成で自動再生すると、攻撃目標が
    「達成」と判定されるスロットで自動停止し、その過程がチェーン表示・状態表で追える。
    さらに Ex-Ante(A01)・バランシング(A03)・LMD バランシング(A04)・アバランチ
    (A07)を、攻撃が宣言する上書きを外した `merge` プリセット(既定値のまま)で
    自動再生すると proposer boost・緩和策が効いて攻撃目標が未達のまま推移し、終了
    スロットで停止することが観測できる。バウンシング(A05)を committee = エポック分割の
    上書きを保ったまま切替窓の上書きだけを外した `merge` プリセット(切替窓 on)で
    自動再生すると、起点の切替がエポック先頭スロットに限られて正直者全員が各エポックで
    同じ target に投票し、切替窓 off では錨のまま進まない finalized が前進して跳ねが
    止まることが観測できる(既定の L では活性停止に達してよい)。同様に `current`
    プリセット(切替窓 off・unrealized on)で自動再生すると、本モデルの unrealized
    (起点より古い justified しか実現し得ない枝の除外)は起点の跳ねに作用せず、両方 off と
    同一の推移になることが観測できる。
20. 攻撃と手動介入を併用したシナリオを保存・再読込・再実行すると、同一の生成行動と
    同一の判定推移が再現される。
21. フォーク数(神視点の木で、最新 finalized ブロックを根とする部分木の葉の数)が、
    未実行の指定を含めて 4 に達している状態でフォーク作成を指定すると UI が受け付けず、
    finality が進んでフォーク数が減ると再び受け付ける。分断・エクイボケーションで
    自然にフォーク数が 5 以上になっても UI は制約しない。
22. スラッシング on で証拠(二重提案・二重投票・包囲投票)が生じると、その証拠を
    取り込んだブロック以降の枝のチェーン状態でエクイボケータのステークが 0 になり、
    その枝を head とするバリデータの状態表のステーク項目に反映され、以後その枝の
    fork choice 重み・finality 閾値から除外されることが観測できる。証拠を取り込んで
    いない枝では変化せず、スラッシング off では変化しない。
23. inactivity leak on で、ある枝の finalized が N エポック進まないと、以後エポック
    ごとに、そのエポックの target 投票がその枝に取り込まれていないバリデータのステークが
    率 r で減り、finalized が進むと減少が止まることが、その枝を head とするバリデータの
    状態表で観測できる。leak off では減らない。
24. 攻撃目標が 2 段(攻撃者ステーク比率 ≥ 1/3、続いて安全性違反)の攻撃(A14)を
    実行すると、比率の推移と閾値到達スロット、続く第 2 段の判定推移がスロット軸上に
    表示される。
25. バリデータごとの初期ステークを UI から設定でき、シナリオに保存され、既定は
    全員等しい。
26. 刷新後の UI について、(a) 標準的な PC の画面幅の初期表示でチェーン表示と状態表が
    スクロールなしに画面面積の過半を占め、(b) ブラウザ既定の見た目のままのフォーム
    部品が無く、(c) パネル常駐の説明文が無く、(d) UI のスタイル定義に色・余白・文字
    サイズ・書体の直書きが無いことが機械検査で確認でき、(e) OS のテーマ設定に追従し
    手動切替で上書きでき、(f) 選定した書体が 3 用途に適用されていることが検証でき、
    かつ人間が実ブラウザで確認して承認している。
27. 安全性違反を達成する攻撃(A10・A12)を既定実行構成で実行すると、違反が判定される
    までに神視点で、攻撃者集合のうち合計ステークが全体の 1/3 以上となるバリデータの
    FFG 証拠(二重投票または包囲投票)が成立しており、その証拠を取り込んだ枝では
    スラッシングが効くことが観測できる(可罰性)。
28. 攻撃一覧の行の選択と実行開始の操作以外の入力なしに、スロットが自動的に進んで
    チェーン表示・状態表・判定推移が各スロットで更新され、途中で一時停止・再開でき、
    攻撃目標が達成と判定されたスロットで停止し、停止後にカーソルで任意の過去スロットへ
    巻き戻せる。
29. main に push すると deploy workflow が成功で終わり、
    `https://nyxfoundation.github.io/consensus-sim/` を開くとその push の内容が表示される。
    テストまたはビルドが失敗する commit では workflow が失敗で終わり、公開中の内容は
    直前の成功版のまま変わらない。この観測は人間が GitHub 上で行い、完了の承認条件とは
    しない。Atlas Builder 側の裏づけは `consensus-sim/scripts/ci.sh` を clean install 状態で
    実行して exit 0 で終わること、および生成された `dist/` が相対パス参照で自己完結する
    ことの機械検査とする。

## 必須対応事項

1. バリデータ(プロポーザーとアテスター)・ブロック・投票を主要素とし、ブロックへの
   投票・証拠の取り込み(チェーン状態)を持ち、committee 割当と proposer boost を
   プロトコルパラメータとして持つ最抽象モデルを構築する。時間はスロット刻みで進む。
2. バリデータ数は 4〜10 体で設定可能とし、既定は 4 体とする。各バリデータには
   認知性の高いカタカナ人名(アリス、ボブ等)を割り当てる(具体的な選定は
   Atlas Builder の裁量)。
3. 最抽象レベルに見合った簡約プロトコル骨格を実装する。スロット s は提案・投票・末の
   3 つの観測時点を持つ。提案時: プロポーザーが (s, 提案) の View(s−1 末までの知識)に
   fork choice を計算して parent を決め、その祖先に未取り込みの投票・証拠を body に
   取り込んだブロックを公開する。投票時: そのスロットの committee に属するアテスターが
   (s, 投票) の View(スロット s のブロックまでと s−1 までの投票)から投票する。投票の
   head は毎スロット fork choice(GHOST 系)で決め、FFG 部分 (source, target) は
   エポックごとに決める: そのエポックで最初に投票するスロットで head の枝から定め
   (source = head のチェーン状態の justified、target = そのエポックのチェックポイント)、
   同じエポックの以後の投票では繰り返す(Ethereum の attestation がエポックに 1 回である
   ことに対応し、正直者は FFG 相反を起こさない)。head の枝に取り込まれた投票から
   justified / finalized が決まる(必須対応事項 29)。committee(既定は全員、他にサイズ c
   をシードから決定的に割当、およびエポック分割 — 各バリデータがエポック内でシードから
   定まる 1 スロットにだけ投票する Ethereum 型の committee 構造)は初期条件から導出し、
   プロポーザーはラウンドロビンとする。proposer boost は「スロット s のプロポーザーが
   提案したブロックを、あるバリデータが (s, 投票) までに受信していれば、そのバリデータの
   スロット s の fork choice 計算においてのみ、そのブロックに committee 総重み × boost の
   追加重みが付く(遅延して届いた提案には付かない)」と定義し、既定値は 0.4 とする。
   fork choice とチェックポイント比較のタイブレークは BlockIndex の全順序で行い、骨格の
   規則として明示する。Gasper の shuffling の正確なアルゴリズムや報酬は持ち込まない。
4. シミュレーションは完全決定的とする: 同一シナリオ(シードを含む)から同一の実行結果が
   再現される。
5. 各バリデータの状態を個別に観測できる: 状態表のセル展開等により、そのバリデータから
   見えているブロック木・投票・head・justified/finalized 状態、head のチェーン状態
   (各バリデータのステーク)と head ブロックの body(取り込まれた投票・証拠)、および
   各投票がどのブロックを支持したかを確認できる。
6. UI はチェーン表示(下半分に状態表を伴う)と型一覧の 2 ページで構成する。ネットワーク
   表示・全体表示は設けない。
7. チェーン表示の下半分に状態表を備える: 行 = バリデータ、列 = スロット(チェーン表示の
   slotIndex と横位置が揃う)とし、セルにはそのスロット時点の head / justified /
   finalized / ステーク / View の要素のうち、UI から動的に選択した項目を表示する。View の
   詳細をどこまで展開表示するかは Atlas Builder の裁量。他バリデータとの差分がある箇所は
   強調表示する。局所視点/神視点の切り替えは設けず、チェーン表示は常に全バリデータの
   情報を重ねた表示とする。状態表は標準的な PC の画面幅で約 10 スロット分の列が収まる
   列幅とし、超過分は横スクロールで辿れる。
8. 型一覧ページは独自のレイアウトとする: ヘッダーバー(ページ切替・テーマ切替)だけを
   残し、スロットバー・操作盤・バリデータ数の設定は載せない。幅の概ね 8 割に依存
   グラフを、残り約 2 割にフォーカス中の型(宣言をコメント込みで、および依存先・依存元の
   型の一覧 — 選ぶとフォーカスが移る)を表示する。ページを開いた直後は依存グラフ最上段の
   先頭の型がフォーカスされている。完了は人間が実ブラウザで確認して承認したことを
   条件とし、承認前に完了扱いにしない。
9. 介入として、バリデータ集合の分断、バリデータの稼働状態変更(オンライン稼働/
   オンライン停止/オフラインの 3 状態。停止は提案・投票をやめるが受信は続け、
   オフラインは送受信とも遮断されビューが凍結する。復帰はいずれも「オンライン稼働」に
   戻り、オフライン復帰後は復帰スロット以降の通常の伝搬のみで追いつく)、二重提案・
   二重投票(エクイボケーション)、特定メッセージの遅延・欠落(受信者集合を指定でき、
   既定は全員)、特定バリデータの投票先指定(スロット s の投票の head/target をその
   バリデータの View に含まれるブロックから、source を View 内の枝のチェックポイントから
   指定する。target のエポックはスロットから定まる。未指定時は従来どおり fork choice と
   FFG の規則が選ぶ。同じエポックで既に投じた FFG 部分と異なる指定は証拠になる)、
   および取り込みの省略(プロポーザーの次の提案で、body に取り込む投票・証拠のうち
   指定したものを省く。未指定時は取り込み規則どおりすべて取り込む)を、UI からスロット
   境界で指定できる。
10. プロポーザーが次に提案するブロックの parent を、UI からスロット境界で、その
    プロポーザーの View に含まれるブロックの中から指定できる(フォーク作成)。未指定時は
    従来どおり View 上の fork choice が選ぶブロックを parent とする。フォーク数は
    神視点の木(公開済み全ブロック)で、最新の finalized ブロックを根とする部分木の
    葉の数と定義する(finalized ブロックだけなら 1)。フォーク作成の指定は、指定時点で
    「現在の神視点フォーク数 + 未実行のフォーク作成指定によって増えるフォーク数 +
    この指定で増えるフォーク数(parent が既に子を持つなら 1、葉なら 0)」が 4 を超える
    場合 UI が受け付けない(分断等の他の介入で自然に生じるフォーク数は制約しない)。
    攻撃の戦略が生成するフォーク作成にも同じ上限を適用し、超える行動は破棄する
    (必須対応事項 21 の破棄と同じく「破棄」の印付きで介入一覧に残す)。
11. 任意の過去スロットへの巻き戻しができ、その時点の全バリデータの状態が正確に再現される。
12. シナリオ(初期条件+手動介入の列+高々 1 つの攻撃)の localStorage への保存・
    再読込・再実行ができる。
13. すべての操作は説明書なしで UI 上から実行できる(新しい攻撃をライブラリへ追加する
    行為はコード編集であり、ここでいう操作には含めない)。
14. コア(モデル・プロトコル層)の設計は、より具体的な抽象レベルの将来追加を妨げない。
15. アプリ内に型一覧ページを設け、ドメイン層の本質的仕様モジュールの型を上から下への
    依存グラフ(他のどの型にも依存しない型が最上段)として表示する。シミュレーション上の
    制約モジュールの型は表示しない。表示内容は実装の型定義と一致させる。生成方法・
    描画方法は Atlas Builder の裁量。
16. 最後の必須対応事項を完了扱いにする前に、徹底的に自己批判的・客観的な総点検を実施し、
    発見した問題をすべて解消する。特に次の 3 観点を重視する:
    (1) ESSENCE・仕様・実装の対応に高度な一貫性があり完全に整合していること、
    (2) 無駄が徹底的に削ぎ落とされ、引き算の美学でシンプルかつ洗練された設計・実装・
    ドキュメント・コメントであること、
    (3) 複雑な条件の組み合わせでもバグが混入していないこと。
    (3) の裏づけ手段(テスト戦略)は Atlas Builder の裁量とする(完全な証明は柱 2 の
    Lean で行う将来事項であり、今回スコープでは求めない)。点検の観点・発見・対処は
    記録として残す。必須対応事項が改訂で追加されるたびに、追加分について総点検を
    再実施し、前回の記録に追記する。
17. 攻撃の形式体系をドメイン層に構築する: 攻撃 = (攻撃者集合の条件, 攻撃目標, 戦略) の
    3 つ組を型として定義する。攻撃者集合の条件は、バリデータの空でない部分集合が満たす
    べき条件(人数の下限、または初期ステーク比率の下限)であり、柱 2 の定理が「条件を
    満たす任意の集合について」と述べる対象である。条件を満たす具体的な攻撃者集合を
    束ねたものが攻撃の実行(シナリオの構成要素)である。攻撃目標は観測可能な述語の
    非空な列(通常は長さ 1。先頭から順に達成を判定し、末尾まで達成した時点で攻撃目標の
    達成とする)、戦略は各スロット境界で攻撃者が観測している状態(攻撃者集合の全 View
    の合併 — 攻撃者同士は即時・完全に情報共有する — と予定表)を入力に、その境界での
    攻撃者の行動を決める規則(固定の介入列は戦略の特殊ケース)とする。
18. 攻撃者の能力範囲は 2 つの基底で定める。(i) 公開: 自分名義のメッセージを、任意の
    内容で(ただしブロックの parent・body と投票の head/source/target は自分の観測状態に
    あるものからのみ構成できる — 偽造不能)、任意の時機に、任意の受信者集合へ公開する。
    保留・選択配送・沈黙(公開しないこと)を含む。(ii) 配送: 正直者のメッセージの到達を
    受信者ごとに遅らせる(公開から最大 d スロット)、または欠落させる。分断は (ii) の
    対称な集合である。介入の全種(エクイボケーション・提案 parent 指定・投票先指定・
    沈黙・遅延と欠落・取り込みの省略・分断)はこの基底の糖衣であり、戦略はその語彙で
    行動を記述する。遅延上限 d は攻撃が前提として宣言するネットワーク仮定である。
19. 攻撃目標述語は神視点(公開済み全ブロック・全投票と各枝のチェーン状態)で毎スロット
    境界に評価し、少なくとも次の 4 種を備える:
    安全性違反(公開済みブロック木上に、互いに祖先関係にない 2 つのチェックポイントが
    存在し、それぞれが自分の枝のチェーン状態で finalized である)、
    活性停止(公開済みブロック木のどの枝でも finalized が直近 L スロットの間に進んで
    いない)、
    リオーグ(ある正直バリデータの head が直前スロットの head の子孫でないブロックに
    移る事象を 1 回と数え、いずれかの正直バリデータで累計 k 回以上。既定 k = 1)、
    攻撃者ステーク比率(いずれかの正直バリデータの head 枝のチェーン状態で、攻撃者
    集合の合計ステーク ÷ 全バリデータの合計ステークが閾値 θ 以上)。
    達成/未達とその根拠を述語の段階ごとにスロット軸上に表示する。
20. 戦略はドメイン層の TypeScript(攻撃ライブラリ)として定義する。UI は攻撃の選択・
    攻撃者集合とパラメータの設定・実行・可視化を担い、戦略を UI 上で組み立てる機能は
    設けない。
21. 攻撃はシナリオの構成要素とし(初期条件+手動介入の列+高々 1 つの攻撃)、手動介入と
    併用できる。戦略が各スロットで決めた行動はそのスロットの介入として生成し、既存の
    介入一覧・状態表・チェーン表示上で攻撃者の行動と分かる印付きで表示する(手動編集は
    しない)。同一スロット・同一バリデータで手動介入と矛盾する行動は手動介入を優先して
    破棄し、破棄した行動も「破棄」の印付きで介入一覧に残す。攻撃者バリデータは
    チェーン表示と状態表の各表示で識別できるようにする。
22. アプリ内に攻撃一覧ページを設け、冒頭に攻撃の形式体系の定義(3 つ組・攻撃者の
    能力範囲・攻撃目標述語)を表示し、続いて攻撃ライブラリの全攻撃を表(列: 攻撃名/
    出典(`essences/deep-research-report.md` の攻撃 ID を含む)/前提(プリセット名+
    上書き・遅延上限 d)/攻撃者集合の条件/攻撃者に必要な能力/攻撃目標(述語の列)/
    戦略の要約/既定実行構成)で表示する。行を選ぶとその攻撃の既定実行構成がシナリオの
    初期条件として提案され、変更は任意で、実行開始の操作をするだけで自動再生(必須対応
    事項 31)が始まる。表の内容は実装の攻撃ライブラリから導出して一致させる。
23. 攻撃ライブラリに次の 12 攻撃を定義する(ID は `essences/deep-research-report.md`
    の攻撃 ID。各攻撃は前提をプリセット名+上書きと遅延上限 d で宣言し、攻撃者集合の
    条件を満たす既定実行構成(バリデータ数・初期ステーク・攻撃者集合・攻撃パラメータ・
    自動再生の終了スロットに、宣言した前提を合わせたもの。具体値は裁量)を持つ):
    A01 Ex-Ante リオーグ(保留+時機; 前提 phase0; リオーグ)、
    A02 proposer boost 逆用リオーグ(前提 merge; リオーグ)、
    A03 バランシング(前提 phase0; 活性停止)、
    A04 LMD バランシング(エクイボケーション+選択配送; 前提 merge + 割引 off; 活性停止)、
    A05 バウンシング(競合 justified 間の跳ね; 前提 merge + 切替窓 off + committee =
    エポック分割; 活性停止)、
    A06 エポック境界 finality 遅延(提案遅延で target 分裂; 前提 merge; 活性停止)、
    A07 アバランチ(秘匿エクイボケーションブロック列; 前提 phase0 + forkChoice = GHOST;
    リオーグ)、
    A09 1/3 超の棄権による finality 停止(前提 merge; 活性停止)、
    A10 34% 二重投票による二重 finality(同一エポックの 2 つの target への投票を選択
    配送で分ける; 前提 merge; 安全性違反)、
    A11 51% 多数派 fork choice 支配(前提 merge; リオーグ)、
    A12 66% 履歴支配(過去 finalized に反する finalize、包囲投票の証拠を自枝で省略; 前提
    merge; 安全性違反)、
    A14 inactivity leak 増幅(正直者を分断して leak させ攻撃者比率を 1/3 以上へ; 前提
    merge; [攻撃者ステーク比率 ≥ 1/3, 安全性違反])。
    それぞれ既定実行構成で自動再生すると終了スロットまでに攻撃目標が達成される。
    A01・A03・A04・A07 は、宣言した上書きを外した `merge` プリセット(既定値のまま)では
    proposer boost・緩和策により未達となる。A05 は committee = エポック分割の上書きを
    保ったまま切替窓の上書きだけを外した `merge` プリセット(切替窓 on)では、起点の
    切替がエポック先頭スロットに限られて跳ねが止まり finalized が前進する(既定の L では
    活性停止に達してよく、未達は求めない)。`current` プリセット(切替窓 off・unrealized
    on)では、本モデルの unrealized が起点の跳ねに作用しないため両方 off と同一の推移と
    なる(緩和の観測対象としない)。A10・A12 は成功条件 27 の可罰性を伴う。
24. プロトコルパラメータ(committee 割当方式・サイズ c、proposer boost、緩和策、罰則)と
    シードを UI から個別に設定でき、プリセット(phase0 / merge / current)で一括設定
    でき、シナリオに保存される。
25. 各バリデータはステーク(重み)を持つ。初期値は全員等しく、シナリオの初期条件として
    バリデータごとに UI から設定可能とする。ステークは枝ごとのチェーン状態であり、
    初期ステークとその枝に取り込まれた投票・証拠から決定的に導出する(View 型には
    持たせない)。fork choice の重みはそのバリデータの head のチェーン状態のステークで、
    FFG の 2/3 閾値は当該枝のチェーン状態のステークで計算する。ステークは状態表の
    表示項目に含める。
26. 罰則をプロトコルパラメータとしてモデル化する。スラッシング(on/off): 証拠(二重
    提案・二重投票・包囲投票)を取り込んだブロック以降、その枝のチェーン状態で
    エクイボケータのステークを 0 として扱い、以後の重み・閾値から除外する(証拠を
    取り込んでいない枝では効かない)。inactivity leak({N, r} | off): 枝のチェーン状態で
    finalized が N エポック(既定 4)進んでいないと発動し、エポックごとにそのエポックの
    target 投票がその枝に取り込まれていないバリデータのステークを率 r で減らし、
    finalized が進めば停止する。Ethereum の二次関数的な罰則額や報酬は持ち込まない。
27. 緩和策をプロトコルパラメータとしてモデル化する。fork choice 規則(GHOST: 全投票を
    数える | LMD-GHOST: 各バリデータの最新投票のみ数える)、エクイボケーション割引
    (on: View 内で投票の証拠(二重投票・包囲投票)が成立した瞬間から、そのバリデータの
    投票を fork choice の重みから除外 — 即時・局所・fork choice のみ | off)、justified
    チェックポイント切替(独立した 2 スイッチ。切替窓 on: fork choice の起点とする
    justified の切替をエポック内の先頭区間に限る | off。unrealized on: 各枝について、
    取り込まれた投票をエポック末を待たずに集計したときに justified となるチェックポイント
    (unrealized justified)を計算し、fork choice の起点より古い justified しか実現し得ない
    枝を候補から除外する | off。Ethereum ではバウンシング対策として前者が先に、後者が
    後に導入された。細部は Ethereum に準拠しつつ裁量)。既定は `merge` プリセットとする。
28. ドメイン層を「本質的仕様(モデル)」と「シミュレーション上の制約」の 2 モジュールに
    分割し、前提事項の判定基準(柱 2 の定理を述べ、証明するのに要る定義か)で振り分ける。
    振り分けは総点検の点検項目に含める。
29. チェーン状態をモデル化する: 各ブロックについて、錨ブロックからそのブロックまでの
    枝に取り込まれた投票・証拠と初期ステークから、ステーク・justified・finalized を
    決定的に導出する。取り込まれた投票がその枝の FFG リンクとして数えられるのは、
    source と target がその枝のそれぞれのエポックのチェックポイントであるときに限る
    (Ethereum の取り込み妥当性に対応。同じブロックが連続するエポックのチェックポイントで
    あるリンクも正当)。source が justified で source → target のリンクが 2/3 に達すれば
    target が justified、さらに target.epoch = source.epoch + 1 なら source が finalized
    となる(隣接はエポック番号で判定し、ブロックのスロットから推定しない)。View の
    justified / finalized / ステークはその View の head のチェーン状態を指し、fork choice は
    View の投票(メッセージ層)で、finality と罰則はチェーン状態(取り込み層)で計算する。
30. 前提事項の UI デザイン方針に従って UI の視覚設計と情報設計を刷新する(デザイン
    基盤: デザイントークン・書体・統一部品・操作盤、および全表示への適用)。刷新の
    完了は、人間が実ブラウザで確認して承認したことを条件とし、承認前に完了扱いに
    しない。
31. 攻撃の自動再生を備える: 攻撃一覧で行を選び実行開始の操作をすると、初期条件の入力・
    スロット送りの手操作なしに、スロットが一定の間隔で自動的に送られ、各スロットの
    提案・投票・攻撃者の生成行動・攻撃目標の判定推移がチェーン表示・状態表・介入一覧に
    順次現れる。一時停止・再開ができ、攻撃目標が達成と判定されたスロットで自動停止し、
    達成しない場合は既定実行構成が宣言する終了スロットで停止する。停止後は巻き戻し・
    介入の追加・プロトコルパラメータの変更ができる。送りの間隔の既定値は裁量とし、
    速度調整は任意対応事項とする。
32. 本質的仕様モジュールのコメント(型定義と規則の説明)は日本語で書く。識別子(型名・
    フィールド名)は英語のまま。型一覧に表示される型はすべてコメントを持つ。
    シミュレーション上の制約モジュール・UI・テストのコメントは対象外(英語のまま)。

- バックエンド/サーバは構築しない(静的 SPA を維持する)。
- マルチユーザー・共有機能は作らない。
- M1 既存コードとの互換維持はしない(完全置き換え)。
- シナリオの JSON ファイルのインポート/エクスポート機能は作らない(localStorage 保存で
  足りる)。
- 分岐比較 — 過去に戻って別の介入を試し、複数の歴史を並べて比較する機能は作らない。
- ネットワーク表示・全体表示(バリデータごとのカードを並べる別画面や、チェーン表示との
  並置)は作らない。各バリデータの状態・ビューの個別観測は状態表のセル展開(必須対応
  事項 5・7)で行う。
- ネットワーク層(BGP/Eclipse: A15〜A17)・クライアント実装差(A18)・PBS/MEV-Boost
  (A19〜A21)・提案者 DoS(A13)の攻撃は収録しない。最抽象モデルの語彙(バリデータ・
  ブロック・投票・メッセージ配送)の外にあり、理想の対象外とする。
- Lean 形式化・形式検証付き新アルゴリズム提案(柱 2)。攻撃の形式体系も形式化の対象に
  含める(現段階では実施しない。攻撃の形式体系が完成し、攻撃ライブラリの全攻撃
  (必須対応事項 23 の 12 件)がその体系で記述・可視化できた状態が観測されたら、
  update-essence で必須対応事項/任意対応事項への昇格を検討)
- より具体的な抽象レベルの追加 — デルタ/離散イベント刻み、shuffling・報酬を含む Gasper
  完全意味論、確率的ネットワーク(現段階では実施しない。committee・boost・緩和策・
  チェーン状態・ステークと罰則を含む最抽象モデルでは表現できない疑問や攻撃に実際に
  ぶつかり、人間がそう判断したら、update-essence で昇格を検討)
- 新アルゴリズムの実装・比較機能 — 簡約骨格以外をモデル上で動かすこと。プロトコル
  パラメータとプリセットの範囲内の切替(必須対応事項 24〜27)は簡約骨格に含む
  (現段階では実施しない。柱 2 の着手時に併せて update-essence で再判断)
- SMT ソルバー的な網羅的バグ探索 — 事前に設定した内容で網羅的にバグを探索する機能
  (現段階では実施しない。総点検を経た後にモデル層のバグが新たに発見されたら —
  テストによる裏づけでは足りないと観測されたら — update-essence で昇格を検討)
- weak subjectivity / long-range 攻撃(A08)(現段階では実施しない。成立にはバリデータの
  退出(ステーク引き出し)と途中参加して同期するノードの 2 概念が要り、参加者固定・
  錨ブロック合意済みで開始する現行モデルには存在しない。バリデータの退出・途中参加を
  モデルに加えると人間が判断したら、update-essence で昇格を検討)
- 戦略を UI 上で組み立てる規則ビルダー、および攻撃記述用の DSL(現段階では実施しない。
  攻撃ライブラリの全攻撃が体系で記述・可視化でき、その後に追加した攻撃でも 3 つ組の
  定義変更が不要だったと観測されたら、update-essence で昇格を検討)
- バリデータ数上限(10 体)の拡大(現段階では実施しない。4〜10 体では再現できない攻撃に
  実際にぶつかったら、update-essence で昇格を検討)
- 複数攻撃の同時実行 — 1 シナリオに 2 つ以上の攻撃を載せること(現段階では実施しない。
  単一の攻撃では記述できない合成攻撃(例: A14 と bouncing の組合せ)をライブラリに
  入れたいと人間が判断したら、update-essence で昇格を検討)
- realized justification のエポック境界での更新 — 本モデルのチェーン状態は取り込みの
  たびに集計するため常に unrealized であり、Ethereum の realized / unrealized の区別は
  持たない(現段階では実施しない。その区別が要る疑問や攻撃に実際にぶつかり、人間が
  そう判断したら、update-essence で昇格を検討)

## 用語

- **最抽象モデル**: バリデータ(プロポーザー/アテスター)・ブロック・投票を主要素とし、
  committee 割当・proposer boost・緩和策・罰則をプロトコルパラメータとして持ち、
  メッセージ層(View)とチェーン状態層(取り込み)の 2 層を持ち、バリデータごとの
  ステークをチェーン状態として持つコンセンサスの形式化。時間はスロット刻みで、
  スロット内に提案・投票・末の 3 つの観測時点を持つ。
- **バリデータ**: シミュレーションの参加者。ネットワーク分断・稼働状態変更等の介入は
  バリデータ単位で指定する。
- **プロポーザー/アテスター**: ブロックを提案する役割のバリデータ/投票する役割の
  バリデータ。アテスターはそのスロットの committee に属するバリデータ。
- **committee**: あるスロットで投票するアテスターの集合。割当方式はプロトコルパラメータ
  (既定は全員、他にサイズ c をシードから決定的に割当、エポック分割 = 各バリデータが
  エポック内でシードから定まる 1 スロットにだけ投票)。
- **予定表**: 初期条件(ProtocolParams・シード)から導出されるプロポーザーと committee の
  割当 `{proposerOf, committeeOf}`。全バリデータが知る公開情報。プロポーザーは
  ラウンドロビン。
- **初期条件**: バリデータ数・初期ステーク・プロトコルパラメータ・シードの組。シナリオの
  一部であり、プロトコルが読む入力。
- **観測時点**: `{slot, phase: 提案 | 投票 | 末}`。View の座標。ブロックは提案時に、
  投票は投票時に公開される。
- **proposer boost**: スロット s のプロポーザーのブロックを (s, 投票) までに受信した
  バリデータの、スロット s の fork choice においてのみそのブロックに付く追加重み
  (committee 総重み × boost)。既定 0.4。
- **取り込み**: プロポーザーが提案ブロックの body に投票・証拠を含めること。正直な
  プロポーザーは View 内の未取り込み分をすべて取り込む。**取り込みの省略**はその一部を
  意図的に含めない介入/攻撃者の行動。
- **証拠(エクイボケーションの証拠)**: 同一バリデータの相反する 2 メッセージの対。
  二重提案・二重投票・包囲投票の 3 形。独立したメッセージ型ではなく、相反 2 メッセージが
  揃った View で成立し、ブロックに取り込まれる。
- **チェックポイント**: `{epoch, block}`。ある枝のエポック e のチェックポイントは、
  その枝上でエポック e の先頭スロット以前の直近のブロック(先頭スロットにブロックが
  あればそれ、無ければそれ以前の最も新しい祖先。Ethereum に準拠)。境界スロットが空なら
  同じブロックが連続するエポックのチェックポイントになる。
- **チェーン状態**: あるブロックについて、錨ブロックからそのブロックまでの枝に
  取り込まれた投票・証拠と初期ステークから決定的に導出される、ステーク・justified・
  finalized(いずれもチェックポイント)の組。View の justified / finalized / ステークは
  head のチェーン状態。
- **プロトコルパラメータ**: committee 割当方式・サイズ c、proposer boost、fork choice
  規則、エクイボケーション割引、justified チェックポイント切替(切替窓・unrealized の
  2 スイッチ)、スラッシング、inactivity leak。初期条件の一部。既定は `merge` プリセット。
- **プロトコルプリセット**: Ethereum の実在時点に対応する名前付きのプロトコル
  パラメータの束(phase0 / merge / current)。攻撃はプリセット名+個別上書きで前提を
  宣言する。
- **ステーク**: バリデータの重み。枝ごとのチェーン状態であり、初期ステークと取り込み
  内容から導出する。fork choice の重みと FFG の 2/3 閾値の計算に使い、罰則により減る。
- **罰則**: スラッシングと inactivity leak の総称。チェーン状態のステークを減らす
  プロトコルパラメータ。
- **緩和策**: fork choice 規則(GHOST | LMD-GHOST)・エクイボケーション割引・justified
  チェックポイント切替の総称(必須対応事項 27)。proposer boost と罰則は別のプロトコル
  パラメータとして数えるが、攻撃を未達にする働きは同じく観測の対象とする。
- **スラッシング**: 証拠を取り込んだブロック以降の枝のチェーン状態で、エクイボケータの
  ステークを 0 として扱う罰則。プロトコルパラメータ(on/off)。
- **inactivity leak**: 枝の finalized が N エポック進まないときに発動し、エポックごとに
  その枝に target 投票が取り込まれていないバリデータのステークを率 r で減らす罰則。
  プロトコルパラメータ({N, r} | off)。
- **エクイボケーション割引**: View 内で投票の証拠が成立した瞬間から、そのバリデータの
  投票を fork choice の重みから除外する緩和策(即時・局所・fork choice のみ)。
  プロトコルパラメータ(on/off)。
- **justified チェックポイント切替**: fork choice の起点とする justified チェック
  ポイントの切替規則。独立した 2 スイッチ: 切替窓(on: エポック内の先頭区間に限る)と
  unrealized(on: unrealized justification により古い justified しか実現し得ない枝を
  除外)。プロトコルパラメータ。
- **unrealized justification**: 枝に取り込まれた投票をエポック末を待たずに集計したときに
  justified となるチェックポイント。
- **エポック**: 4 スロットの区切り。チェックポイントの単位。
- **錨ブロック**: 開始時点で全バリデータが finalized と合意している木の根。
  ジェネシスの代替。エポック 0 のチェックポイント。
- **ビュー**: あるバリデータがある観測時点に持つ知識 `{blockTree, votes}`。バリデータと
  観測時点は View の座標であり、内容ではない。
- **投票**: `{validator, slot, head, source, target}`。head は GHOST 系 fork choice の
  先頭支持(LMD 部分。LMD かどうかはプロトコルパラメータ)、source/target は FFG 部分の
  チェックポイント対で、正直者はエポックごとに 1 度だけ決め、同じエポックの投票で
  繰り返す。
- **投票先指定**: 特定バリデータのスロット s の投票の head/target をその View 内の
  ブロックから、source を View 内の枝のチェックポイントから指定する介入。
- **メッセージ参照**: (送信者, スロット, 種別) に、公開済みなら個体を添えたメッセージの
  名指し。未公開のメッセージも名指せる。
- **受信者集合**: 遅延・欠落の介入で、そのメッセージが遅延・欠落する相手のバリデータ
  集合(既定は全員)。攻撃者はこれで自分のメッセージの保留と選択配送を行う。
- **状態表**: チェーン表示の下に置く、行 = バリデータ・列 = スロットの表。セルの表示
  項目は UI から動的に選択でき、他バリデータとの差分がある箇所を強調表示する。
- **操作盤**: プロトコルパラメータ・介入・シナリオの操作系を集約した、主役(チェーン
  表示・状態表)より小さい面積の領域。
- **デザイントークン**: 色・余白・文字サイズ・書体の単一の定義。UI のスタイル定義は
  ここから参照する。
- **稼働状態**: バリデータの 3 状態。オンライン稼働/オンライン停止(提案・投票を
  しないが受信は続く)/オフライン(送受信とも遮断されビューが凍結)。復帰はいずれも
  オンライン稼働に戻る。
- **フォーク**: ブロック木上の競合するブランチ。フォーク作成 = 提案ブロックの parent を
  プロポーザーの View 内のブロックから指定する介入。
- **フォーク数**: 神視点の木(公開済み全ブロック)で、最新の finalized ブロックを根とする
  部分木の葉の数。フォーク作成の指定は、未実行の指定を含めてこれが 4 を超えない範囲で
  のみ受け付ける。
- **神視点**: 公開済み全ブロック・全投票(公開の記録)と各枝のチェーン状態を重ねた
  大域の木。チェーン表示はこれを示し、攻撃目標述語はこれで評価する。
- **分断**: 指定したバリデータ集合間のメッセージが届かなくなる介入。
- **エクイボケーション**: 同一バリデータによる二重提案・二重投票・包囲投票。
- **包囲投票**: 同一バリデータの 2 投票で、一方の source → target がもう一方の
  source → target をエポックで外側から包むもの。Casper FFG の可罰条件。
- **可罰性**: 安全性違反が起きたとき、神視点に合計ステーク 1/3 以上の証拠が存在すること。
  Casper FFG の accountable safety。
- **決定性**: 同一シナリオ(シードを含む)から同一の実行結果が再現されること。
- **シナリオ**: 初期条件+手動介入の列+高々 1 つの攻撃の保存単位(localStorage に保存)。
- **攻撃**: (攻撃者集合の条件, 攻撃目標, 戦略) の 3 つ組。現時点の暫定定義。
- **攻撃者集合の条件**: 攻撃者として振る舞うバリデータの空でない部分集合が満たすべき
  条件(人数の下限、または初期ステーク比率の下限)。条件を満たす具体的な集合を束ねた
  ものが攻撃の実行。
- **前提**: 攻撃が成立する環境の宣言。プロトコルパラメータ(プリセット名+上書き)と
  遅延上限 d。
- **公開/配送**: 攻撃者の行動の 2 つの基底(必須対応事項 18)。公開は自分名義の
  メッセージを任意の内容・時機・受信者集合で出すこと、配送は正直者のメッセージの到達を
  遅らせる(最大 d スロット)か欠落させること。
- **攻撃目標**: 攻撃の成否を判定する観測可能な述語の非空な列(通常は長さ 1)。神視点で
  毎スロット境界に、先頭から順に評価する。種類は安全性違反・活性停止・リオーグ・
  攻撃者ステーク比率。
- **リオーグ(事象)**: 正直バリデータの head が、直前スロットの head の子孫でない
  ブロックに移ること。
- **攻撃者ステーク比率**: いずれかの正直バリデータの head 枝のチェーン状態における、
  攻撃者集合の合計ステーク ÷ 全バリデータの合計ステーク。
- **戦略**: 各スロット境界で、攻撃者が観測している状態(攻撃者集合の全 View の合併と
  予定表)を入力に、その境界での攻撃者の行動(必須対応事項 18 の能力範囲)を決める規則。
  固定の介入列は戦略の特殊ケース。
- **既定実行構成**: 攻撃ごとに宣言する、攻撃者集合の条件を満たすバリデータ数・
  初期ステーク・攻撃者集合・前提・攻撃パラメータ・自動再生の終了スロットの組。攻撃一覧の
  行を選ぶとシナリオの初期条件として提案される。
- **自動再生**: スロットが一定の間隔で自動的に送られる再生。一時停止・再開ができる。
  攻撃の自動再生は攻撃一覧の実行開始の操作で始まり、攻撃目標の達成スロットまたは
  既定実行構成の終了スロットで停止する(必須対応事項 31)。
- **攻撃ライブラリ**: ドメイン層の TypeScript として定義された攻撃の集合。攻撃一覧
  ページの表はここから導出する。
- **本質的仕様/シミュレーション上の制約**: ドメイン層の 2 モジュール。前者は柱 2 の
  定理を述べ、証明するのに要る定義(型と意味論)、後者は本シミュレータの都合で定める
  もの。型一覧は前者のみ表示する。
