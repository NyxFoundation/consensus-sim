# 総点検の記録

最終リリース前に、自己批判的・客観的な総点検を次の 3 観点で実施した。
本書はその点検内容・発見した問題・対処の記録である(2026-08-30 実施)。

## 点検の方法

- 観点 (1)(2) は、要求文書(ESSENCE.md)の成功条件 13 項・必須対応事項
  16 項・非対応事項の全項目を、実装ファイル・テストと突き合わせる全数
  トレースで点検した。
- 観点 (3) は、全介入種を同時投入した敵対的な複合シナリオのテスト群
  (`tests/domain/combined.test.ts`)を新設し、決定性・巻き戻しの prefix
  性・シリアライズ往復・可視性の単調性・複合意味論を機械的に固定した。
- 点検後、`npm run typecheck` / `npm test` / `npm run build` の全ゲートを
  実行し、すべて exit 0 を確認した。

## 観点 (1) 要求・仕様・実装の整合

成功条件 13 項・必須対応事項 16 項は全項目が実装とテストにトレースできた。
非対応事項(バックエンド・マルチユーザー・シナリオ JSON ファイル入出力・
分岐比較・Lean・スラッシング・攻撃プリセット等)は、該当コードが存在しない
ことをソース全走査で確認した。

発見した問題と対処:

1. **実ブラウザ検証スクリプトが旧 UI 前提で全チェック失敗する状態だった**
   (`scripts/verify-ui.mjs`)。視点切替タブ・旧タブ名・プレースホルダ等、
   撤去済みの UI を前提にしていた。→ 現行 UI(4 タブ・状態表・カタカナ人名・
   歴代 F バッジ・介入パネル・型一覧)に合わせて全面改稿した。
2. **セル展開の投票表が「各投票」を表示していなかった**。バリデータ毎の
   最新投票(LMD)に畳んでいたため、二重投票の片方と過去スロットの投票が
   UI から観測できなかった。→ セル展開はビュー内の全投票を個別に列挙する
   表示に改め、二重投票の両方が見えることをテストで固定した。チェーン表示
   下の表は fork choice が実際に数える「最新投票(LMD)」の表示として存置
   (表題どおり)。
3. **ネットワーク表示のカードに稼働状態が出ていなかった**。「各バリデータの
   状態がパッと見で分かる」に対し、停止・オフラインが読めなかった。→
   ドメイン層に稼働状態の導出(`operatingStateAt`)を追加し、カードに
   停止中/オフラインのフラグを表示するようにした。
4. **README の 3 箇所が実装とずれていた**(シード操作 UI があるかのような
   記述・フォーク上限の曖昧な表現・テーマ切替の記載漏れ)。→ いずれも
   実装どおりの記述に修正し、機能列挙が二重化していた Status 段落を圧縮した。

対処せず記録に留める判断:

- **フォーク作成上限の解釈**: 要求は「同時に存在するフォークが 4 本を
  超える場合 UI が受け付けない」。実装は「介入キュー内のフォーク作成指定を
  同時 4 件まで」とするより厳しい近似で、禁止側は常に満たす(指定を削除
  すれば枠が戻る)。ブロック木は追記のみで指定由来のフォークは消えないため、
  両者が乖離するのは「指定したが実際にはフォークが生じなかった」端例のみ。
  厳密なフォーク数の動的計数より、見て数えられる単純な規則を優先した。
  (追記: Essence 改訂でフォーク数が「最新 finalized ブロックを根とする部分木の
  葉数」と定義されたため、近似を撤去しドメインの `forkCount` /
  `forkCountAfter` による厳密計数へ置換した。)
- **finalized の表示粒度**: justified は集合、finalized は最前線 1 個を表示
  する非対称は、歴代の確定がブロック木の F バッジで全て読めるため実害なしと
  判断し存置。

## 観点 (3) 複雑な条件の組み合わせ

新設した敵対的複合テスト(12 ケース)で次を機械的に固定した:

- **全介入種同時**(分断+停止+オフライン+二重提案+二重投票+遅延+欠落+
  フォーク作成)での決定性(再計算の完全一致)、巻き戻しの prefix 性
  (途中スロットまでの再計算が全走行の先頭部分と一致)、シリアライズ往復後の
  再実行同一性、可視性の単調性(一度見えたメッセージは見え続ける)。
- **停止とオフラインのスパン重複**(同一バリデータ、部分重なり)での沈黙・
  凍結・追いつきの正確な境界。
- **遅延と分断の同時充足**: 遅延期限が切れても分断中は届かず、両条件が同一
  スロットで揃って初めて到達する(点単位配送の意味論)。
- **分断内のエクイボケーション**: 二重投票が分断の片側に閉じ込められ、解消
  後に全員が同一の LMD 解決に到達する。

発見した問題と対処:

1. **巻き戻し後の稼働状態操作が、未来に予約済みのスパンを無告知で削除する**
   (稼働状態コントロールの表示は「次スロット時点」の状態を読むのに、変更
   操作は未来のスパンまで巻き込んで閉鎖・削除していた)。無効なスパンは
   生成しないが、意図しないシナリオ改変だった。→ 変更操作の対象を表示と
   同じ「次スロットに掛かるスパン」に限定し、未来のスパンは温存するよう
   修正。回帰テストを追加した。

複合テスト自体からの新規バグ検出はゼロ(ドメインの複合意味論は初回から
全ケース通過)。上記 1 件は UI 層のキュー操作の点検で発見した。

## 残る既知の制約

- A05 バウンシングと justified チェックポイント切替の緩和策: A05 は前提
  (merge + 切替 off + committee = エポック分割、4 体・攻撃者 1・seed 0)で
  成立し、justified が 2 枝の間を跳ね続けて finalized が錨から進まない。
  切替の上書きだけを外した merge(window)では、起点の切替がエポック先頭
  スロットに限られるため、開幕(エポック 1〜3)の跳ねの後、エポック 4 以降は
  正直者全員が各エポックで同じ target に投票し、finalized が slot 48 から
  前進して跳ねが止まる(既定の L = 12 の活性停止は緩和が効く前の slot 12 で
  達成される)。current(unrealized)は起点(view 内の最高 justified)を変えず
  候補を刈るだけなので起点の跳ねに作用せず、off と全スロット同一の推移になる。
  1 票 = ステークの 1/4 という粒度が Ethereum(最終スロットの committee は
  1/32)と異なるため、window の効きが Ethereum より遅い(最初の finalized が
  slot 48)。この 3 通りの推移は `tests/domain/attackLibrary.test.ts` に固定した
  (要件は R-009 の判断でこの観測可能な事実に改訂済み)。
- 新しいビジュアル(モノクロ基調・フラット・高密度)の見た目の最終確認は、
  実ブラウザでの目視(`npm run dev`、または `npm run build && node
  scripts/verify-ui.mjs`)による。自動テストは DOM 構造・文言・介入挙動を
  固定しているが、レンダリング結果の審美判断は含まない。

## 追記: 参照型の改訂(2026-09-03)

要求文書の参照型が全面改訂されたのに伴い、ドメイン層を次のとおり改めた
(総点検の再実施は、改訂の適用がすべて済んだ後に本書へ追記する)。

- **識別子のソート分離**: `ValidatorIndex` / `SlotIndex` / `EpochIndex` /
  `BlockIndex` / `Stake` を型レベルで区別した(数値リテラルは各ソートへ
  入るが、ソート間の代入は型検査が拒む)。`BlockIndex` は同一性だけを担い、
  fork choice の子の選択・同一エポックのチェックポイント比較・
  エクイボケーションの 2 票の並びに使う全順序は `order.ts` に骨格の規則
  として 1 箇所で明示した。
- **番兵の廃止**: `Block` を `錨 {index, slot} | 提案 {index, parent, slot,
  proposer, body}` の和型にし、錨の parent = −1 / proposer = −1 という番兵を
  撤去した。
- **チェックポイント `{epoch, block}`**: 投票の source / target と
  チェーン状態の justified / finalized をチェックポイントにした。境界
  スロットが空なら同じブロックが連続するエポックのチェックポイントになる。
  取り込まれた投票が枝の FFG リンクとして数えられるのは、source と target が
  その枝のそれぞれのエポックのチェックポイントであるときに限り、finalize の
  隣接判定はエポック番号で行う。これにより、以前の簡約「空の境界スロットに
  フォールバックしたチェックポイントは finalize されず 1 エポック遅れる」
  (隣接判定がブロックの slot のエポックを使っていた)は撤回され、
  `{e, B} → {e+1, B}` のリンクも正当になった。
- **投票先指定**: head / target はビュー内のブロック(target のエポックは
  スロットから定まる)、source はビュー内の枝のチェックポイントから指定する
  形にし、シナリオの保存形式も `source: {epoch, block}` へ改めた。
- UI はチェックポイントを `B4@e1` の形で表示する。
- **観測時点と座標を持たない View**: `Instant = {slot, phase: 提案 | 投票 |
  末}` を導入し、`View = {blockTree, votes}` からバリデータとスロットを外した
  (両者はビューを計算する関数の引数 = 座標)。(s, 提案) は s−1 末までの知識、
  (s, 投票) はスロット s のブロックまでと s−1 までの投票、(s, 末) は s まで
  すべて。攻撃者集合の観測状態(View の合併)も座標を持たない View になった。
- **FFG 部分のエポック単位の決定**: 正直者の (source, target) は、その
  エポックで最初に投票するスロットで head の枝から定め、同じエポックの以後の
  投票では繰り返す(投票先指定の source / target はこれに優先する)。正直な
  即時配送の実行では finality の推移は変わらない(エポックの 2 スロット目
  以降の投票は従来 source = target のエポックで無効だったものが、正当だが
  余分なリンクの繰り返しに変わるだけ)。分断・攻撃下では、収束したスロットの
  エポックの FFG が固定されるため finality の再開が 1 エポック遅れる。
- **初期条件と予定表**: `SimulationConfig` を `InitialConditions =
  {validatorCount, initialStakes, params, seed}` に改名し、`Schedule =
  {proposerOf, committeeOf}` を本質的仕様に置いた。本質的仕様は割当方式ごとの
  構造(全員 / 順列の先頭 c 体 / エポックの順列をスロットへ配る)だけを述べ、
  シードからの具体的な順列(hash32 + mulberry32 の Fisher–Yates)は
  `sim/schedule.ts` に移した。fork choice の解決(`resolveView`)は予定表を
  引数に取る。
- **メッセージ参照の統一**: `MessageRef = (sender, slot, kind: proposal |
  vote)` に、公開済みなら個体(ブロックは index、投票は内容全体)を添えた
  2 形へ畳んだ(従来の block / vote / proposal / attestation の 4 形を廃止)。
  個体の無い参照は送信者・スロット・種別の全メッセージを名指す(未公開の
  メッセージの保留・選択配送)。正直者のメッセージを個体で名指す行動は能力
  範囲外、攻撃者自身のメッセージはどちらでも「withhold」。シナリオの保存形式
  は version 2(旧形式は読み込まず破棄)。
- **二重投票の選択配送**: 攻撃者の二重投票の 2 票は同じ (sender, slot, vote)
  参照を持つため、統一後の参照では公開前に片方だけを名指せない。そこで
  二重投票の介入に `split = {first, second, untilSlot}`(1 票目は first へ、
  2 票目(指定 head の票)は second へ即時、他は untilSlot から)を持たせ、
  A04 の選択配送をこれで記述した。公開基底(内容・時機・受信者集合)の糖衣で
  あり、能力範囲は変えていない。
- **攻撃ライブラリの再調整**(意味論は不変、機構の維持): A10 は同一エポックの
  第 2 の target(slot 5 の B3、slot 9 の B7)を投票先指定で明示し(未指定
  だとエポック最初の target が繰り返される)、A14 は各枝の tip への投票に
  その枝の justified / チェックポイントを source / target として明示した。
  A04 は、両陣営の最新投票が同じ枝に揃ったら戦略を止める(割引で均衡が
  崩れた後も提案遅延を続けると、エポック境界ブロックの遅延で target が割れる
  A06 型の停止になってしまい、merge 既定での「未達」が観測できない)ように
  し、活性停止の L を 20 にした(割引下の最初の finalize は slot 13、正直
  実行は slot 9)。12 攻撃の達成/未達テストはすべて緑。

## 追記: 参照型の改訂 (3)(4) — 証拠の 3 形・切替の 2 スイッチ・行動の 2 基底(2026-09-03)

- **Equivocation の 3 形**: `Equivocation` を 二重提案 `{validator, slot, blocks}` /
  二重投票 `{votes}` / 包囲投票 `{votes}` の和型にし、投票の 2 形は相反 2 票の
  対だけを内容とする(エクイボケータと成立スロットは `equivocatorOf` /
  `evidenceSlotOf` で導く。成立スロット = 後の票のスロット)。検出
  (`equivocationsIn`)は、同一スロットの相反はスロット内の対ごと、スロット
  横断(同一 target エポックで target の異なる 2 票、および
  source₁.epoch < source₂.epoch < target₂.epoch < target₁.epoch の包囲)は
  バリデータの **相異なる FFG 部分の代表(最初の票)どうし** に限って対を
  作る。正直者はエポック内で同じ FFG 部分を繰り返すため証拠を生まず、
  攻撃者が同じ FFG 部分を繰り返しても対が爆発しない(裁量の正規化。相反の
  意味論は ESSENCE の定義そのもの)。スラッシングは 3 形すべて、割引は投票の
  証拠 2 形で発火する(テストで固定)。
- **R-007 の撤回**: 「スロットを分けた同一エポックの FFG 二重投票は本モデルの
  証拠に当たらない」という了承済みの簡約は、Equivocation の 3 形の導入により
  撤回した。A10 / A14 の攻撃者票は FFG 二重投票の証拠として神視点に成立する
  (成功条件 27 の可罰性)。
- **投票先指定と証拠**: 同じエポックで既に投じた FFG 部分と異なる target を
  指定すると、その 2 票が証拠になり次ブロックに取り込まれてスラッシングされる
  ことをテストで固定した(`tests/domain/steering.test.ts`)。
- **切替の 2 スイッチ**: `checkpointSwitch = {window, unrealized}` の独立
  2 スイッチにした。window は起点(`forkChoiceRoot`)だけを、unrealized は
  候補の刈り込み(`viableBlocks`)だけを決め、両 on は両方が同時に効く。
  プリセット: phase0 / merge は on・off、current は off・on。
- **leak の和型**: `inactivityLeak = {delayEpochs, rate} | "off"`。
- **行動の 2 基底**: `PublishBase`(自分名義のメッセージの content / timing /
  receivers / silence)と `DeliverBase`(正直者メッセージの hold ≤ d または
  drop、受信者集合)を型として置き、`basesOf(action, attackers, schedule)` で
  介入語彙を基底へ展開し、`capabilityOf` は `withinRange(bases)` で判定する。
  これにより能力範囲の実装が ESSENCE 必須対応事項 18 と一致するよう次の
  2 点を正した(意味論の変更ではなく実装の逸脱の是正。Recommendation R-011):
  (i) 攻撃者自身のメッセージの保留は「任意の時機」であり d に縛られない
  (従来は自他を問わず d で切っていた)、(ii) 分断は配送基底の対称集合なので、
  閉じた分断は長さ ≤ d のときだけ範囲内、開いた分断は欠落として範囲内
  (従来は無条件に範囲内)。二重投票の split は Publish(content)+
  Publish(receivers) に展開される(R-010 の確認)。
- **前提**: `AttackPremise = {preset, overrides?, maxDelay}` を本質的仕様に
  置き、既定実行構成の `maxDelay` は前提から束ねる(`defaultParams`)。
- **攻撃ライブラリの再設計**(可罰性 成功条件 27):
  - A10: 攻撃者は偶数スロットで枝 A、奇数スロットで枝 B の target に投票し、
    各票をその枝の正直者にだけ届けてスロット 12 まで保留(公開の受信者集合と
    時機)。分割は欠落ではなく遅延にし(d = 8)、スロット 12 に視界が合流した
    後のスロット 13 の正直提案が FFG 二重投票の証拠を取り込んで攻撃者を
    スラッシングする。違反判定は slot 11。
  - A12: 分岐側のエポック 3 の投票(錨 → B12)がエポック 2 の投票(B4 → B8)を
    包囲する。正直者はスロット 15 の提案で正直チェーンに取り込み(攻撃者は
    そこで 0)、攻撃者は自枝の提案で省略する。正直チェーンでは攻撃者が 0 に
    なった結果、正直者 1 体の票だけで justify / finalize が進む(スラッシング
    が閾値からも除外する ESSENCE の規則の帰結)ため、攻撃者は以後の提案の
