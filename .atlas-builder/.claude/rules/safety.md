I-004: PROJECT_ROOT/ESSENCE.md and PROJECT_ROOT/essences/** are human-only.
I-007: Over-Project Agent may edit PROJECT_ROOT implementation files (the main implementation path).
I-008: Agent Runtime High-Risk Zone requires explicit high-risk tracking (over whatever such paths exist — e.g. .github/workflows/**, and .claude/** when the target embeds an agent).
I-010: Todo cannot be done without evidence.
I-011: Human/Essence stop conditions and idle-cycle safety stops must halt the loop before more autonomous work.
I-013: Each completed Atlas Builder cycle is represented by at most one Git commit.
I-014: Atlas Builder cycles start only from a clean Git worktree.
I-015: Agents may inspect Git status/diff, but may not stage or commit directly.
I-016: Cycle commit failure is a hard stop; loop diffs must not mix across cycles.
I-017: Every stop is visible: it exists in canonical state (Recommendation/Blocker or a directly evaluated canonical file/phase fact), in the `just status` output, and in the loop's exit message, together with the resume instruction.
I-018: At most one canonical-write window (loop/once/resume/supervise/init/bootstrap or any mutating state command) runs per control plane at a time (single-flight lock; nested transitions and in-cycle state writes inherit the ancestor's slot). A holder is stale only when process absence is positively established; permission/sandbox/probe uncertainty never authorizes lock reclamation.
I-019: A gated loop invocation is side-effect-free: no run record, no counter change, no commit.
I-020: An agent cycle commit never contains changes to PROJECT_ROOT's human-gated control files (ESSENCE.md and its essences/** attachment assets, and — where the target embeds an agent — CLAUDE.md, .claude/**); they enter Git history only through human checkpoints. Of these, ESSENCE.md is the only human requirement-input file a human writes (essences/** holds the human-placed non-Markdown assets it references, §2.1.5; Atlas Builder develops the agent-runtime config through the supervised High-Risk workflow, §12.1); ESSENCE.md enters history exclusively through resume checkpoints after init. README.md is NOT in this set: it is an ordinary implementation file the agent owns (§11.1) and its diffs ride in the cycle commit.
I-021: Gate evaluation fails closed: unreadable or shape-corrupt gate-holding state stops the loop, a crashed predicate exits as a hard error (never as "no"), and no framework transition rebuilds an unreadable state file from defaults.
I-022: Gate triage is advisory and read-only: the triage session mutates neither project files nor canonical state (its CLI settings make the target OS-sandbox read-only; its only freely writable path is the CONTROL_ROOT/.agent/tmp/triage/ handoff, and its only other write surface is ask-gated — the live CONTROL_ROOT/.claude/settings.json deployment repair (§28.5-3), which proceeds only with the human's explicit approval on the permission prompt), and the only transition it can lead to is a resume the human explicitly confirms on the terminal.
I-024: No Atlas Builder-launched Agent receives secret environment variables or read access to Atlas Builder's defined secret input surfaces (target .env/.env.*/secrets/credentials plus the enumerated home credential stores in §11.4). Secret-bearing verification is run by the human outside the Agent session; only its exit status and a redacted summary may enter evidence/state. Before every Atlas Builder checkpoint, the exact staged blobs are scanned for a conservative set of high-confidence credential signatures; a hit aborts before commit and reports filenames only. This is a backstop, not a claim of complete secret detection.
I-027: The Essence interview is advisory and read-only: the interview session mutates neither project files nor canonical state (its only freely writable path is the CONTROL_ROOT/.agent/tmp/essence/ handoff; its only ask-gated write surfaces are the live settings repair (§28.5-3) and — new mode only — the direct ESSENCE.md install fallback and the essences/ asset install (one file at most 3 segments deep, §2.1.5)), and ESSENCE.md is installed only through a human-confirmed act: primarily by the human-only wrapper after the human reviews the full draft on the terminal and explicitly confirms; in new mode, as a fallback second path, by a session Write the human explicitly approves on the permission prompt after reviewing the same full draft on screen — I-004 preserved: the installed content originates from the human's answers and confirmation, never from unreviewed agent text.

The test is §18.4's: "does this command mean anything in a distributed, bound control plane?"

## Additional hard limits

- Never edit `PROJECT_ROOT/ESSENCE.md` or anything under `PROJECT_ROOT/essences/**` — both are human-only (I-004). You may read essences/ assets, but never write, move, rename, or delete them; the guard hook, settings deny, and sandbox denyWrite all fence the whole `essences/` prefix (META.md §2.1.5, §11.3). Their changes never ride a cycle commit — an essences/ edit enters Git history only through a human `just resume` checkpoint (I-020), the same as ESSENCE.md.
- Never read or exfiltrate `.env`, `.env.*`, `secrets/**`, `config/credentials.json`.
- Never launch `claude` from inside an Agent session. An embedded target runtime is executable, untrusted product content and must go through a project-defined isolated runner (I-003, §10).
- Never run `rm -rf`, `sudo`, `chmod -R`, `chown`, `git push`, `git reset --hard`, `git clean -fd`, or pipe-to-shell downloads.
- Never run `git add` or `git commit` directly; cycle checkpoint commits are created only by `loop.sh`.
- Never run `atlas-builder state resume` / `resume.sh` / `just resume` / `just state resume`; the resume transition (stop-gate release / human-update checkpoint) is human-only (META.md §13.3, I-011).
- Never run `loop.sh` / `stop.sh` / `once.sh` / `init.sh` / `doctor.sh` / `triage.sh` / `supervise.sh` / `essence.sh` / `watch.sh` / `claude-trust.sh` / `atlas-builder trust ensure` (or their `just` shortcuts): loop/once spawn autonomous sessions and own cycle commits; stop paces the loop's lifecycle (graceful drain, META.md §19.1-7 — when you want the loop to pause, record a canonical Recommendation instead, §13.4); supervise is the human-present path across a High-Risk ask gate; init re-renders the binding; triage and essence launch human sessions; doctor/trust-check inspect `~/.claude.json`, which is outside the Agent secret boundary; watch is a resident full-screen TUI that never returns (a cycle that launches it wedges, META.md §15.3 — the same information is already yours through the permitted `state status` / `should-stop`). All are human-only operations (META.md §18.2, I-024). `bootstrap.sh` needs explicit human approval (ask).
- Never write to the essence attestation ledger (`CONTROL_ROOT/.agent/state/essence_attestations.jsonl`) or to `PROJECT_STATE_ROOT/state/project.json`: they anchor the §13.1-10 attestation chain and only `atlas-builder state` transitions may touch them.
- Control-plane surfaces (`CONTROL_ROOT` の `CLAUDE.md`, `.claude/**`, `scripts/**`, `templates/**`, `recipes/**`, `justfile`, `META.md`, `README.md`, `.agent/prompts/**`, binding anchors) are immutable/denied in every bound Agent session, including supervise (META.md §11.3, I-028). Framework work belongs to the maintainer plane. `PROJECT_ROOT/README.md` remains an ordinary implementation file (§11.1).
- Dependency changes require the human, and the guard hook (`atlas-builder hook pre-tool`) is the whole gate — settings.json holds no install rule, because a settings `ask` outranks a hook `allow` and would prompt on every install (META.md §11.2). The hook auto-allows exactly two shapes: (1) a single install whose packages are ALL trusted — on the curated list in the hook, or declared by the project's ESSENCE.md (`deps: npm:<pkg>, pypi:<pkg>, crates:<pkg>, go:<mod>, lean:<pkg>`); (2) a materialization that names no package of its own (`pnpm install`, `npm ci`, `bun install`, `--frozen-lockfile`, `uv sync`, `uv pip sync <file>`, `pip install -r <file>`, `poetry install`, `pipenv sync`, `cargo fetch`, `cargo update`, `go mod download`, `lake update`, `lake exe cache get`) — the dependency set it expands was already gated when the manifest was written. Unknown packages, extra flags, custom registries, git/URL version specs, and compound commands still ask; the one compound exception is a single plain `cd <dir> &&` prefixed to an allowed install, with the cd target checked against the allowed roots.
- Dependency manifests (`package.json`, `pyproject.toml`, `Pipfile`, `requirements*.txt`, `Cargo.toml`, `go.mod`, `lakefile.lean`, `lakefile.toml`, `lake-manifest.json`, `lean-toolchain` — and every lockfile / package-manager config in the same ask set: `package-lock.json` / `npm-shrinkwrap.json` / `pnpm-lock.yaml` / `yarn.lock` / `bun.lock*` / `.npmrc` / `.yarnrc*` / `.pnpmfile.cjs` / `bunfig.toml`, `uv.lock` / `poetry.lock` / `Pipfile.lock` / `pip.conf`, `Cargo.lock` / `.cargo/config*`, `go.sum`) are always `ask` — through Edit/Write and through Bash mutations alike. This is the single decision point for the dependency set, so never route around it (a manifest written by shell redirect would turn the materialization allow into a bypass).
- When you do need a dependency the human has not authorized, batch the whole decision into ONE install command instead of asking N times, and raise a Recommendation that the human declare the recurring ones in the Essence (`deps:`) — that is the sanctioned way for future installs to run unattended. Only framework maintainers extend the curated hook list in the source maintainer plane.
- These boundaries are enforced by permissions and hooks; treat a denied action as a design signal, not an obstacle to route around.
